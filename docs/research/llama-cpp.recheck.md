### Managed-child mode makes the server exit gracefully on the stdin exit line and exit(1) on stdin EOF, so it also provides parent-death protection and a graceful Windows shutdown path

Status: corrected

Only after the model has loaded. role.setup(shutdown_handler), which starts the stdin monitor thread, is called after ctx_server.load_model() returns and the READY state is about to be sent. During loading, neither the exit line nor stdin EOF is read, and signal handlers are not installed either, so a load can only be aborted by killing the process. An orphan whose parent died mid-load keeps loading and exits only once the load finishes. Keep the Job Object (Windows) and an explicit kill path for the loading phase.

Source: tools/server/server.cpp lines 666-712 (order of load_model, server_install_signal_handlers, role.setup); tools/server/server-common.cpp lines 2244-2270

### Recommendation: on macOS prefer the HF-bucket single-file binary as the Tauri externalBin

Status: unverifiable

## Things the research missed

### Backend DLLs are also loaded from the current working directory: a DLL-planting vector for an agentic app

ggml_backend_load_best enumerates and LoadLibrary's every file matching ggml-<name>-*.dll / ggml-<name>.dll in the executable directory AND the process's current directory (and whatever GGML_BACKEND_PATH names). If the sidecar is spawned with cwd set to a user workspace or cloned repository, a file such as ggml-cuda.dll or ggml-cpu-zen4.dll in that folder is loaded and its ggml_backend_score/init code runs. The researcher listed the search paths but not the consequence. Always set the child's cwd to an app-controlled directory and never pass GGML_BACKEND_PATH from the user's environment. The same cwd rule can be used deliberately: an optional CUDA pack in an app-data folder is discovered if cwd points there (Windows DLL search also resolves its cudart/cublas dependencies from cwd).

Source: ggml/src/ggml-backend-reg.cpp lines 480-598 at b12110

### llama-server inherits LLAMA_ARG_* environment variables, which can silently enable dangerous or network features

Every option has an env form and env values apply whenever the flag is not given explicitly. A user or parent environment containing LLAMA_ARG_TOOLS=all, LLAMA_ARG_AGENT, LLAMA_ARG_MCP_SERVERS_JSON, LLAMA_ARG_UI_MCP_PROXY, LLAMA_ARG_CONNECT (peer-to-peer tunnel), LLAMA_ARG_HF_REPO, LLAMA_ARG_MODELS_PRESET, LLAMA_ARG_CORS_ORIGINS, LLAMA_ARG_SSL_*, LLAMA_ARG_SLOT_SAVE_PATH or HF_TOKEN changes sidecar behaviour without any flag on the command line. 'Leave --tools unset' is not enough. Spawn with a cleared environment plus an allowlist (PATH/SystemRoot/TEMP, LLAMA_API_KEY, LLAMA_CACHE pointing at an app dir, optionally LLAMA_SERVER_ROUTER_PORT).

Source: common/arg.cpp (set_env on each option, lines 3282-3500); tools/server/README.md parameter table

### Semver covers only the C API; the sidecar interface has no stability contract even on 'stable' tags

docs/release.md ties MAJOR/MINOR/PATCH to include/llama.h. Flags, defaults, log lines, HTTP fields and the router-child protocol can change in any minor release, and stable tags have appeared roughly every 1-2 weeks (v0.7.0 10-15, v0.8.0 10-28, v0.9.0 11-04). 'Pin to stable' therefore reduces churn but does not give compatibility; the app needs a contract test suite run against every candidate build (flags accepted, /health, /props keys, streaming tool-call shape, managed-child lines) and a single adapter module that owns argument construction.

Source: docs/release.md at b12110; git tag dates as reported in the research; b12242 commit titles on the releases page

### Release assets can be extracted and inspected in CI; concrete bundle contents and sizes

Windows: 53 files, 106 MB unpacked; minimal llama-server set is about 90 MB (ggml-vulkan.dll alone 42 MB, CPU variants 21 MB, llama-server-impl.dll 10 MB, llama-common.dll 8.4 MB). llama-connect.exe (11.5 MB peer-to-peer tunnel), llama.exe, the other tools, their *-impl.dll and ggml-rpc.dll can be removed. macOS: 11 Mach-O files, about 31 MB, and libggml-rpc/libggml-blas cannot be removed because they are link-time dependencies. GitHub assets are attested (actions/attest), so `gh attestation verify` can run in the app's CI in addition to a pinned SHA-256.

Source: Extraction of b12110 Windows Vulkan zip and macOS arm64 tarball; .github/workflows/release-publish.yml

### CUDA and Vulkan backends can coexist in one directory, and iGPUs are skipped when a discrete GPU exists

Backends are loaded in a fixed order (cuda before vulkan) and llama.cpp skips a GPU whose device id is already claimed by an earlier backend; integrated GPUs are added only when no discrete GPU was found. So an optional CUDA pack is 'drop ggml-cuda.dll plus cudart64/cublas64/cublasLt64 next to the existing files (or in the cwd)'; no second llama-server build is needed, since every backend zip is the CPU zip plus one DLL. Constraint: a per-machine NSIS install directory is not user-writable, so either install per-user, or keep the whole runtime (or the CUDA pack via cwd) under app data.

Source: ggml/src/ggml-backend-reg.cpp lines 570-598; src/llama.cpp lines 222-286; .github/workflows/release.yml (windows, windows-cuda jobs) and release-publish.yml merge step

### Windows start-up failure modes that produce no stderr at all

llama-server.exe and its DLLs import VCRUNTIME140.dll, VCRUNTIME140_1.dll and MSVCP140.dll. If any import-linked DLL is missing, the Windows loader fails the process before main: no log line, exit status STATUS_DLL_NOT_FOUND (0xC0000135), and by default a modal system error box. A parent that calls SetErrorMode(SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX) passes that mode to the child and suppresses the box. This is Windows loader semantics, not tested here. The app should map 0xC0000135 / 0xC000007B and abort-style exits to specific user messages, and ship the three VC runtime DLLs app-local beside llama-server.exe or install the redistributable.

Source: llvm-readobj --coff-imports on the b12110 Windows binaries; Windows loader semantics (untested in this session)

### Port and identity handling: --port 0 is unusable for readiness polling, and /health cannot identify the server

With --port 0 the socket is bound before load but the chosen port is only logged ('listening on ...') after the model has loaded, so the Rust side must choose the port. Because /health is unauthenticated and SO_REUSEADDR is set on the listener, a stale or foreign server on the same port can answer 200. After /health turns 200, make one authenticated GET /props with the per-launch key; a 401 means a different process owns the port.

Source: tools/server/server.cpp lines 334-345, 659-700; tools/server/server-http.cpp lines 216-228, 252-258, 494-520

### Windows paths: the exe embeds an activeCodePage=UTF-8 manifest

llama-server.exe carries common/win-app.manifest (activeCodePage UTF-8), and main is a plain char** main. Non-ASCII model paths and arguments therefore work on Windows 10 1903 and later only; on older Windows 10 builds argv is in the ANSI code page. Set the app's minimum Windows 10 version accordingly and pass arguments as normal Unicode strings from Rust.

Source: common/win-app.manifest, cmake/win-app.cmake, tools/server/main.cpp; strings in the extracted llama-server.exe

### Router mode needs hardening before it suits an offline single-user app

Defaults: model source is the user's global cache (LLAMA_CACHE), --models-max 4, autoload on (any request naming another model loads it), POST /models downloads from Hugging Face, children inherit the router's env and args. If router mode is chosen for its documented progress events and memory estimates, start it with --models-preset <app ini> (absolute paths), --models-max 1, --no-models-autoload, --offline, LLAMA_CACHE set to an app directory, and the API key in the environment so children enforce it too. The router also gives a pre-load memory estimate (GET /models 'memory' min/max); standalone users can get the same from llama-fit-params, which prints fitted -c/-ngl arguments.

Source: tools/server/README.md lines 2017-2200, 2385-2475; tools/server/server-models.cpp lines 268-330; tools/fit-params/README.md

### Cancellation and single-slot behaviour

There is no cancel endpoint for generation; closing the HTTP connection is the cancel signal (the stream loop checks should_stop / is_connection_closed). /v1/chat/completions/control only ends reasoning. With -np 1 all requests queue on one slot, so background calls (title generation, compaction, sub-agents) block the main chat and evict its KV state; the host prompt cache (--cache-ram) is what restores the previous conversation afterwards, so setting it to 0 to save RAM has a latency cost. Decide between -np 1 with a modest --cache-ram and -np 2 with --kv-unified-per-slot.

Source: tools/server/server-context.cpp lines 5488-5530; tools/server/server-http.cpp lines 686-808; common/common.h lines 637-645; common/arg.cpp lines 1599-1606, 1666-1690

## Final recommendations

- Accept the research as the basis for ARCHITECTURE.md: every decision-critical fact I re-checked held (release model, asset names and sizes, port 9931 and the other changed defaults, multi-file layout, endpoints, no standalone load progress, rewritten tool calling, silent GPU fallback, licences). Two factual corrections: the managed-child stdin shutdown only works after the model has loaded, and the HF-bucket Windows exe is Authenticode-signed by Hugging Face. Runtime behaviour is still untested by both of us (running the downloaded binary was denied here), so schedule a smoke test on real Windows and macOS hardware before freezing the design.
- Pin b12110 (the build behind v0.9.0) from GitHub release assets: resolve it via v0.9.0/nightly-tag.txt, store tag plus SHA-256 in a lockfile, run `gh attestation verify` in CI, and assert the extracted file set. Do not treat the semver tag as an interface guarantee; add a contract test suite (flags, /health, authenticated /props, streamed tool call, managed-child lines) that gates every llama.cpp upgrade.
- Windows: ship the minimal file set from llama-b12110-bin-win-vulkan-x64.zip in one directory (llama-server.exe, llama-server-impl.dll, llama-common.dll, mtmd.dll, llama.dll, ggml.dll, ggml-base.dll, libomp.dll, all 14 ggml-cpu-*.dll, ggml-vulkan.dll; about 90 MB unpacked) plus app-local msvcp140.dll, vcruntime140.dll, vcruntime140_1.dll, the repo LICENSE and LICENSE-LLVM-OpenMP. Remove llama-connect.exe, llama.exe, other tools and ggml-rpc.dll. Sign every exe and DLL with the app certificate. Bundle the directory as a resource and spawn it with tokio::process rather than relying on externalBin copying a single file.
- macOS: decide explicitly between (a) the GitHub tarball, shipping 11 Mach-O files under their soname names (no symlinks) next to llama-server and signing each with hardened runtime, and (b) building llama-server from the pinned tag in your own CI with -DBUILD_SHARED_LIBS=OFF -DGGML_METAL_EMBED_LIBRARY=ON -DCMAKE_OSX_DEPLOYMENT_TARGET=13.3 -DLLAMA_BUILD_IS_DEV=OFF and a fixed CPU target, which yields one Mach-O. Use the HF-bucket single file only if you accept an undocumented layout with no published checksum or attestation. In every case set the app minimum to macOS 13.3, not 13.0.
- Spawn hardening (security-relevant): set the child's cwd to the llama runtime directory or another app-controlled directory, never a workspace; clear the environment and pass an allowlist only; pass --host 127.0.0.1, a Rust-chosen --port, --no-ui, --offline, explicit -c, -np, --cache-ram, and a restrictive --cors-origins since only the Rust core talks to the server; put a random per-launch key in LLAMA_API_KEY; use CREATE_NO_WINDOW and a kill-on-close Job Object on Windows; call SetErrorMode in the parent so a missing DLL does not raise a modal dialog.
- Readiness and identity: poll GET /health until 200 with a process-exit watcher and timeout, then make one authenticated GET /props to confirm the process is yours and to read n_ctx, modalities and chat_template_caps. Do not use --port 0.
- Load progress: choose one of two designs and isolate it behind a single adapter. Either standalone llama-server with LLAMA_SERVER_ROUTER_PORT set and parsing of 'cmd_child_to_router:state:' lines on stdout (internal protocol, unchanged between b12110 and b12242, re-test on every upgrade), or router mode hardened with --models-preset, --models-max 1, --no-models-autoload, --offline and an app-private LLAMA_CACHE, using GET /models/sse. Fall back to an indeterminate spinner if the expected lines never arrive.
- Shutdown: treat hard kill as the baseline on both platforms (the server holds no persistent state in this configuration). During model load it is the only option. After load, SIGTERM on macOS and the stdin exit line in managed-child mode on Windows give a graceful stop; keep a timeout followed by kill.
- GPU policy: run --list-devices at startup and after installing an optional backend; treat a missing expected device as the silent-fallback case and tell the user. Offer CUDA as a post-install pack (ggml-cuda.dll plus the three cudart DLLs, about 565-650 MB download) placed where the backend search finds it, and show the NVIDIA EULA. Provide a user-visible CPU-only switch (--device none) and automatic retry on CPU when a GPU load aborts.
- Tool calling: gate native tools on /props.chat_template_caps.supports_tool_calls; send tool_choice only as the strings auto, none or required; set parallel_tool_calls explicitly; accumulate deltas by index; treat a mid-stream error event and HTTP 500 parser mismatches as retryable with thinking disabled. For models whose template lacks tool support, plan an app-level fallback (tool protocol in the system prompt plus response_format json_schema) or a curated --chat-template-file, and do not combine response_format with tools in one request. Keep a per-model regression suite because this code changes between nightlies.
- Vision and offline guarantee: gate on /props.modalities.vision, convert to PNG or JPEG and send only data: URIs. Reject any http(s) or file:// media URL in the Rust layer before it reaches llama-server, because the server fetches remote URLs itself even with --offline.
- Always drain the child's stdout and stderr, keep the last few hundred lines for error reports, and map known signatures to user messages: 'couldn't bind HTTP server socket', 'invalid device:', 'exiting due to model loading error' with the preceding allocation lines, HTTP 400 exceed_context_size_error, and on Windows exit status 0xC0000135 for a missing DLL.
