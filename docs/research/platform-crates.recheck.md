# platform-crates — re-check

An independent second pass over the research file of the same name. Where the two disagree, this file is the later and better-checked one.

## Corrections

### The rusqlite helper ecosystem caps at rusqlite 0.40: rusqlite_migration 2.6.0 (^0.40.0), tokio-rusqlite 0.8.0 (^0.40.1), deadpool-sqlite 0.14.0 (^0.40.0), refinery 0.10.0 (<=0.40); r2d2_sqlite 0.36.0 and async-sqlite 0.7.0 need ^0.41

Status: corrected

Correct for rusqlite_migration, tokio-rusqlite, deadpool-sqlite, r2d2_sqlite and async-sqlite. Wrong for refinery: refinery-core 0.10.1 (published 2026-10-26) requires rusqlite `>=0.23, <=0.41`, and refinery 0.10.0 depends on refinery-core ^0.10.0, so a fresh resolve gets 0.10.1 and works with rusqlite 0.41. So the only things forcing a 0.40 pin are rusqlite_migration and tokio-rusqlite, both of which are small enough to replace by hand (PRAGMA user_version loop; std::thread + channel actor). Pinning 0.40.2 is still a safe choice, but it is a convenience pin, not an ecosystem-wide cap.

Source: https://crates.io/api/v1/crates/refinery-core/0.10.1/dependencies ; .../refinery-core/0.10.0/dependencies ; .../refinery/0.10.0/dependencies ; same endpoint for the other crates

### rusqlite_migration API: `const MIGRATIONS: Migrations = Migrations::from_slice(&[M::up("...")]); MIGRATIONS.to_latest(&mut conn)`; MIGRATIONS.validate(); schema version stored in PRAGMA user_version; WAL via conn.pragma_update_and_check(None, "journal_mode", &"WAL", |_| Ok(()))

Status: corrected

The one-line const form does not compile with rusqlite_migration 2.6.0: rustc rejects it with E0493 ('destructor of [M<'_>; 1] cannot be evaluated at compile-time'). The README form is two consts: `const MIGRATIONS_SLICE: &[M<'_>] = &[M::up("...")]; const MIGRATIONS: Migrations<'_> = Migrations::from_slice(MIGRATIONS_SLICE);`. With that fix the rest is confirmed by execution: to_latest() applied the migration, validate() passed, PRAGMA user_version read back 1, and the pragma_update_and_check WAL call compiles and runs.

Source: Local compile + run against rusqlite 0.40.2 / rusqlite_migration 2.6.0; https://raw.githubusercontent.com/cljoly/rusqlite_migration/master/README.md (lines 60-80)

### windows-native-keyring-store README warns Credential Manager loses updates under concurrent writes and 'the crate uses a per-user named mutex' to serialise them

Status: corrected

True only for the unreleased main branch. The published 1.1.0 crate (2026-05-24) contains no mutex, no CreateMutexW call and no such README text, and its windows-sys dependency lacks the Win32_System_Threading feature that main added for it. main still carries version = "1.1.0", so the fix is unreleased. With what you can actually depend on today, the app must serialise all Credential Manager writes/deletes itself (one dedicated secrets thread or a global async mutex); nothing protects against a second app instance unless you add your own named mutex or single-instance lock.

### macOS file-based keychain access is tracked by the creating app's designated requirement; self-signed identities work; ad-hoc builds re-prompt per item after each rebuild because their DR is the cdhash; `protected` store needs a provisioning profile (-34018)

Status: unverifiable

Partly confirmed. Apple TN2206 does say keychain items get 'Free access to the keychain item by the creating application and tracked with its DR' and 'Self-signed identities and homemade certificate authorities (CA) work by default for this case'. apple-native-keyring-store 1.0.2 does document `keychain` as the 'legacy keychain' store for apps without a provisioning profile and maps -34018 (errSecMissingEntitlement) in protected.rs. ### With git2's `https` feature, Windows and macOS need no OpenSSL, so `vendored-openssl` is irrelevant for the two shipping targets

Status: corrected

True for Windows, false for macOS. libgit2-sys declares `[target.'cfg(unix)'.dependencies] openssl-sys = { optional = true }` with `https = ["openssl-sys"]`, and lib.rs calls `openssl_sys::init()` under `#[cfg(all(unix, feature = "https"))]`. macOS is cfg(unix). `cargo tree --target aarch64-apple-darwin -i openssl-sys` on a project with `git2 = { version = "0.21", default-features = false, features = ["vendored-libgit2", "https"] }` prints openssl-sys v0.9.118 <- libgit2-sys <- git2; the same command for x86_64-pc-windows-msvc prints nothing. So although libgit2 does TLS through SecureTransport on macOS, the recommended Cargo line still compiles and links OpenSSL there. Without `vendored-openssl` the build needs a Homebrew/pkg-config OpenSSL and will normally link it dynamically, which produces a .app that references /opt/homebrew dylibs absent on end-user Macs. Either add `vendored-openssl` (static OpenSSL built from source: needs perl/make on the macOS runner, adds build time and an OpenSSL CVE surface you do not use for TLS), or drop `https` and do all network git through the system git CLI.

Source: libgit2-sys-0.18.8+1.9.7.crate Cargo.toml.orig lines 32-39 and lib.rs lines 4739-4748; `cargo tree --target aarch64-apple-darwin -e normal -i openssl-sys` run in a scratch project today

## Things the research missed

### The recommended git2 line links OpenSSL on macOS

`git2 = { version = "0.21", default-features = false, features = ["vendored-libgit2", "https"] }` resolves openssl-sys v0.9.118 under libgit2-sys on aarch64-apple-darwin (libgit2-sys gates the dependency on cfg(unix), not on 'unix and not macOS', and calls openssl_sys::init()). A default macOS build therefore either fails without Homebrew OpenSSL or ships a .app that dynamically loads /opt/homebrew OpenSSL dylibs that end users do not have. Decision needed in ARCHITECTURE.md: (a) add `vendored-openssl` and accept perl/make in the macOS build plus an unused OpenSSL in the binary, or (b) use git2 with only `vendored-libgit2` for local operations (status, diff, log, commit, branch) and route clone/fetch/push through a detected system git, which also removes in-app credential handling. Verify the final choice with `otool -L` on the built binary in CI.

Source: `cargo tree --target aarch64-apple-darwin -i openssl-sys` run today; libgit2-sys-0.18.8+1.9.7.crate Cargo.toml.orig and lib.rs

### rmcp already dictates process-wrap 10 and leaves process-tree wrapping to the host

rmcp 3.9.0 has an optional dependency `process-wrap ^10.0` (feature tokio1) and `TokioChildProcess::new(command: impl Into<CommandWrap>)` takes a process_wrap::tokio::CommandWrap. rmcp adds no wrappers itself, so an MCP stdio server spawned from a plain tokio Command gets no Job Object and no process group; on Windows an `npx`/`uvx` launcher's grandchildren (the real server) are orphaned on kill or crash. The host must build the CommandWrap with `.wrap(KillOnDrop)` + `.wrap(JobObject)` + CreationFlags(CREATE_NO_WINDOW) on Windows and `.wrap(ProcessGroup::leader())` on macOS before handing it to rmcp, and must use the same process-wrap major (10.x) or the types will not match. This makes process-wrap the single spawning layer for llama-server, tool commands and MCP servers; the 'hand-rolled app-wide job with the windows crate' alternative cannot cover rmcp-spawned children without a race. rmcp 3.9.0 is also the first version patched for RUSTSEC-2026-0462, so it is a floor.

Source: https://crates.io/api/v1/crates/rmcp/3.9.0/dependencies ; https://static.crates.io/crates/rmcp/rmcp-3.9.0.crate src/transport/child_process.rs lines 1-90 ; https://rustsec.org/packages/rmcp.html

### Windows: Command::new("npx") does not find npx.cmd, and batch files have special spawn rules

Rust std docs: 'For executable files, the .exe extension may be omitted. Files with other extensions must include the extension, otherwise they will not be found', and under 'Batch file special handling': arguments that cannot be safely escaped for cmd.exe 'will result in an error being returned at process spawn' and 'running batch scripts in this way may be removed in the future'. Standard MCP configs use `command: "npx"` / `"uvx"` / `"pnpm"`, which on Windows are .cmd shims (npx) or .exe (uvx). The MCP launcher and any direct-exec tool path need an explicit resolution step (PATH + PATHEXT lookup with the `which` crate 8.0.6, then spawn the resolved .cmd through `cmd.exe /d /s /c` with controlled quoting, or reject unescapable arguments with a clear error). This is a day-one 'MCP servers do not start on Windows' bug class and it interacts with the Job Object requirement because cmd.exe becomes the direct child.

Source: https://doc.rust-lang.org/stable/std/process/struct.Command.html (Command::new, platform notes) ; https://doc.rust-lang.org/stable/std/process/index.html ('Batch file special handling')

### PowerShell default execution policy blocks script files on Windows client

Microsoft: Restricted is 'The default execution policy for Windows client computers. Permits individual commands, but doesn't allow scripts', and the powershell.exe -ExecutionPolicy parameter sets a session-only policy (stored in $Env:PSExecutionPolicyPreference, not the registry; Group Policy still wins). The recommended invocation `powershell.exe -NoLogo -NoProfile -NonInteractive -Command <script>` runs inline code but any .ps1 the model writes and then runs, a Python venv's Activate.ps1, and the .ps1 shims that Node installs for npm/npx (which PowerShell prefers over the .cmd ones) fail with 'running scripts is disabled on this system'. Decide explicitly whether the terminal tool adds `-ExecutionPolicy Bypass` (process scope, the documented setting for an application that 'has its own security model') and surface the Group Policy case as a readable error.

Source: https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1 ; about_powershell_exe (5.1) -ExecutionPolicy

### A blind trailing `exit $LASTEXITCODE` hides cmdlet failures

$LASTEXITCODE 'Contains the exit code of the last native program or PowerShell script that ran'; cmdlets do not set it. Without the suffix, powershell.exe -Command exits 1 when the last command left $? false. With `; exit $LASTEXITCODE` appended, a script whose only failure is a cmdlet error (e.g. Get-Item on a missing path) exits with the stale or null value, i.e. 0, and a script that ran a successful native program earlier and then failed in a cmdlet also exits 0. The wrapper should capture both: e.g. `$__ok = $?; if ($LASTEXITCODE -is [int] -and $LASTEXITCODE -ne 0) { exit $LASTEXITCODE }; if (-not $__ok) { exit 1 }; exit 0`, and must be tested on real 5.1 (this follows from the documented semantics; I did not run it on Windows).

Source: https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_automatic_variables?view=powershell-5.1 ($LASTEXITCODE, $?) ; about_powershell_exe (5.1) exit-code paragraph

### catch_unwind on a blocking thread is not a containment boundary for untrusted parsers

Three independent holes in 'run pdf-extract under catch_unwind with page/size/time limits': (1) stack overflow is an abort, not a panic. RUSTSEC-2026-0187 states for lopdf: 'Because this is a stack-overflow abort rather than a panic!, it cannot be caught with catch_unwind', crashing the whole app from a ~21 KB file (fixed in lopdf 0.42.0, but the class remains for pdf-extract's own recursion and for pdf_oxide). (2) Tauri's official size guide recommends `panic = "abort"` in [profile.release]; if adopted, catch_unwind catches nothing in release builds. (3) A time limit cannot be enforced on a thread: a parser stuck in a loop on a spawn_blocking thread can never be cancelled and leaks a pool thread. The robust design is a short-lived worker process (the app binary re-executed with a hidden subcommand, the same pattern proposed for the macOS reaper) for PDF extraction and other untrusted-format parsing, with a wall-clock timeout, a kill via the Job Object / process group, and a memory cap (JOB_OBJECT_LIMIT_PROCESS_MEMORY on Windows). Record the `panic` profile decision in ARCHITECTURE.md either way.

Source: https://rustsec.org/advisories/RUSTSEC-2026-0187.html ; https://v2.tauri.app/concept/size/ (profile.release with panic = "abort")

### Several recommended crates are at their first non-vulnerable version; the versions are floors, not just 'latest'

RustSec today: zip needs >=9.0.0 (five advisories on extract()/symlinks, one CVSS 9.1); git2 >=0.21.0; lopdf >=0.42.0 (so pdf-extract >=0.12.1); rustls >=0.23.46; tokio >=1.54.1 (1.54.0 has an Interval race) ; rmcp >=3.9.0; tracing-subscriber >=0.3.20 (RUSTSEC-2025-0055). No advisories are listed for rusqlite (since 2021), keyring/keyring-core, process-wrap, portable-pty, tree-sitter, jsonschema, serde-saphyr, pdf_oxide, pdfium-render, similar, dunce, ignore, sha2, image, reqwest. Consequence: commit Cargo.lock, write the minimums as explicit lower bounds in Cargo.toml, and make cargo-deny (advisories + bans for serde_yml/serde_yaml and duplicate libsqlite3-sys/openssl-sys) a required CI check from the first commit rather than a later hardening task.

Source: https://rustsec.org/packages/{zip,git2,lopdf,rustls,tokio,rmcp,tracing-subscriber}.html and the individual advisory pages, fetched today

### SQLite WAL must not live in a roaming or network-redirected directory on Windows

sqlite.org: 'All processes using a database must be on the same host computer; WAL does not work over a network filesystem.' Tauri's `app_data_dir()` resolves to FOLDERID_RoamingAppData on Windows, which enterprises commonly redirect to a network share or sync; `app_local_data_dir()` resolves to FOLDERID_LocalAppData. The storage section should fix the database (and model files, logs, llama-server slots) under app_local_data_dir on Windows and state that the path must be local. The same concern applies to keyring's default Enterprise persistence: choose `persistence = Local` via keyring-core modifiers unless roaming API keys between domain machines is intended.

Source: https://www.sqlite.org/wal.html ; https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri/src/path/desktop.rs (data_dir / local_data_dir doc comments) ; windows-native-keyring-store-1.1.0 src/store.rs

### macOS 'system git' detection must not execute /usr/bin/git blindly

On a Mac without Xcode or the Command Line Tools, /usr/bin/git is a shim that hands off to xcrun and makes macOS pop up the 'install command line developer tools' dialog. A fallback that probes with `git --version` at startup would show that dialog to every non-developer user. Detect with `xcode-select -p` (exit status / path exists) or by checking for a real git in Homebrew/CLT locations first, and only then run git. I could confirm this only from secondary sources (a GHC merge request titled 'Suppress popup dialog about missing Xcode at configure time', Apple forum threads and install guides), not from an Apple reference page, so test it on a clean macOS 13+ VM. On Windows there is no git by default at all; if network git is delegated to the CLI (see the OpenSSL item), the architecture needs a stated answer for Windows users without Git for Windows (prompt to install, or bundle MinGit; I could not reach the Git for Windows release page from here to confirm current MinGit asset names).

Source: https://gitlab.haskell.org/ghc/ghc/-/merge_requests/2351 ; https://developer.apple.com/forums/thread/660641 ; https://mac.install.guide/commandlinetools/9 (secondary)

### Log volume is unbounded with the recommended tracing-appender setup

tracing-appender 0.2.5 rotates only by time, and max_log_files bounds the file count, not bytes. A chat app that forwards llama-server stderr or tool output at debug level can write gigabytes within one daily file. Options that exist today: keep llama-server and tool output out of the tracing pipeline (bounded in-memory ring buffer plus a size-capped per-session file), or use a size-rotating writer: tauri-plugin-log 2.10.1 has max_file_size with RotationStrategy::{KeepAll, KeepOne, KeepSome(n)} (it is `log`/fern based with an optional tracing feature), and logroller 0.1.12 (2026-07-01) offers size-based rotation for the tracing ecosystem (small crate, ~170k recent downloads; not audited by me).

Source: tracing-appender-0.2.5.crate src/rolling.rs ; https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/log/src/lib.rs (lines 54, 139-145) ; https://crates.io/api/v1/crates/logroller

### Using the `keyring` facade forfeits the controls the report itself says are needed

The report recommends `keyring = "4.2"` 'for the simple path'. That path cannot set Windows persistence, cannot disable windows-native-keyring-store's default `search` feature (regex), exposes no modifiers, and on Linux dev/CI machines pulls zbus-secret-service. Since the published Windows store also lacks the cross-process mutex, the app needs its own secrets service thread anyway. Depending directly on keyring-core 1.0.1 + apple-native-keyring-store (feature keychain) + windows-native-keyring-store (default-features = false) behind one small internal trait is barely more code and is the only variant that satisfies the report's own constraints; the trait also gives the dev-build non-keychain store the report asks for.

Source: keyring-4.2.0.crate src/v1.rs and Cargo.toml; windows-native-keyring-store-1.1.0.crate Cargo.toml and src/store.rs

## Final recommendations

- Treat the research as broadly reliable on versions (all ~70 crate versions, dates and MSRVs matched crates.io today) but fix five factual errors before copying it into ARCHITECTURE.md: (1) git2 `https` does pull and link OpenSSL on macOS; (2) the windows-native-keyring-store cross-process mutex is unreleased; (3) process-wrap's `job_handle().terminate()` is unreleased; (4) refinery-core 0.10.1 accepts rusqlite 0.41; (5) the rusqlite_migration const snippet needs a separate `const MIGRATIONS_SLICE: &[M<'_>]`.
- Git: do not ship `git2` with `features = ["vendored-libgit2", "https"]` as written. Preferred: `git2 = { version = "0.21", default-features = false, features = ["vendored-libgit2"] }` for local operations only (no OpenSSL on either target, no in-app credentials) and a detected system git CLI for clone/fetch/push. If in-app HTTPS is required, add `vendored-openssl` for the macOS target and assert with `otool -L` in CI that the binary loads no Homebrew dylibs. On macOS detect git with `xcode-select -p` before ever executing /usr/bin/git; on Windows state what happens when Git for Windows is absent.
- Process control: make process-wrap 10.x (the version rmcp 3.9.0 already depends on) the single spawning layer for llama-server, terminal commands and MCP stdio servers. Windows: `.wrap(KillOnDrop)` + `.wrap(JobObject)` + `CreationFlags(CREATE_NO_WINDOW)`, default features on, kill through the ChildWrapper trait (`start_kill()`/`kill()`), not `job_handle()`. macOS: `ProcessGroup::leader()` plus the reaper helper, which must be prototyped and crash-tested before the document calls it the design. Do not use tauri-plugin-shell for anything long-lived.
- MCP launch on Windows: add an explicit executable-resolution step (PATH + PATHEXT via `which` 8.x); run resolved .cmd/.bat shims through `cmd.exe /d /s /c` with controlled quoting and reject arguments std cannot escape with a clear error. Pass rmcp a pre-wrapped CommandWrap; never a bare tokio Command.
- PowerShell tool: `powershell.exe -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -Command <script>` (make the Bypass a documented, explicit decision), stdin null, the UTF-8 OutputEncoding prefix wrapped in try/catch, and an exit-code epilogue that checks both `$?` and `$LASTEXITCODE` instead of a bare `exit $LASTEXITCODE`. Build a Windows 10 and Windows 11 test matrix for exit codes, encoding and .ps1/.cmd shims before freezing the tool contract.
- Untrusted-format parsing (PDF first, optionally archives): run it in a short-lived worker process with a wall-clock timeout, tree kill and a memory cap, not under catch_unwind on a blocking thread. Decide and record the release `panic` strategy; if `panic = "abort"` is taken from Tauri's size guide, no catch_unwind anywhere in the app can be relied on. Keep pdf-extract >= 0.12.1 (lopdf >= 0.42.0) as the default extractor behind a trait; pdfium-render 0.9.5 with bundled pdfium-win-x64 / pdfium-mac-arm64 remains the fidelity fallback.
- SQLite: `rusqlite 0.40.2` + `bundled` + rusqlite_migration 2.6.0 is a valid pin (SQLite 3.53.2, FTS5 trigram confirmed working). Equally valid and with fewer moving parts: rusqlite 0.41.1 with a ~30-line PRAGMA user_version migration runner and a hand-rolled single-writer thread, since rusqlite_migration and tokio-rusqlite are the only things holding the pin. Whichever is chosen, forbid sqlx and tauri-plugin-sql with a cargo-deny ban, and place the database under app_local_data_dir (never Roaming or a network path) because WAL does not work over network filesystems.
- Secrets: depend on keyring-core 1.0.1 + apple-native-keyring-store 1.0.2 (feature `keychain`) + windows-native-keyring-store 1.1.0 (default-features = false) behind one internal trait, not on the `keyring` facade. One entry per secret via set_secret (<= 2560 bytes), `persistence = Local` on Windows, all writes serialised on one app-owned thread plus a single-instance guard, and a master-key-in-keychain + encrypted-in-SQLite fallback for values over the limit. Verify the macOS per-item re-prompt behaviour on a real ad-hoc build; sign dev builds with one stable self-signed identity.
- Supply chain: commit Cargo.lock and encode security floors as lower bounds: zip >= 9.0.0 (use NoExtract for symlinks or a manual enclosed_name() loop, plus entry-count and size caps), git2 >= 0.21.0, lopdf >= 0.42.0, rustls >= 0.23.46, tokio >= 1.54.1, rmcp >= 3.9.0. Run cargo-deny (advisories, bans for serde_yml/serde_yaml, duplicate `links` crates) as a required CI job from the first commit. Pin `tauri = "2"` explicitly now that 3.0.0-alpha releases are on crates.io.
- HTTP/TLS: standardise on reqwest 0.13 (rmcp and tauri-plugin-updater already use it) and avoid tauri-plugin-http, which is still on reqwest 0.12 and would add a second stack. On the Windows CI image either install NASM or set AWS_LC_SYS_PREBUILT_NASM=1; the prebuilt objects are not used automatically. Build the localhost llama-server client with `.no_proxy()`.
