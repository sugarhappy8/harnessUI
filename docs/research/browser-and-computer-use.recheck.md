# browser-and-computer-use — re-check

An independent second pass over the research file of the same name. Where the two disagree, this file is the later and better-checked one.

## Corrections

### Recommendation: launch with --remote-debugging-port=0 and read <user-data-dir>/DevToolsActivePort ('%d\n%s'); the pipe is more secure but harder from Rust; fd 3/4 and Windows handle inheritance were 'from my knowledge'.

Status: corrected

File format, atomic write, Host-header check and Origin check are confirmed. Three corrections that change the launch decision: (1) Chromium sets the AutomationControlled runtime feature (navigator.webdriver = true) for `--remote-debugging-port=0` AND for `--remote-debugging-pipe` (and --enable-automation, --headless). The source comment says an explicit port number deliberately leaves it unset 'to ensure the browser behaves as it does when not under automation control'. So both transports the researcher weighed mark the user's logged-in browser as automated; only an explicit non-zero port does not. ### Recommendation: build an in-house CDP client on tokio-tungstenite covering 'roughly 25 methods and 10 events'.

Status: corrected

The choice is defensible, but the sizing is too optimistic and its main justification is weaker than stated. The dropped-event risk has not materialised between r1566079 and r1734725 for the gate-critical types. The real work in a hand-written client is lifecycle, not method count: flat-session multiplexing, Target.setAutoAttach recursion with waitForDebuggerOnStart (every new session needs Runtime.runIfWaitingForDebugger), one session per out-of-process iframe (Accessibility.getFullAXTree and Fetch.enable must be issued per session, and click coordinates in OOPIFs need frame-offset translation because Input.dispatchMouseEvent takes main-frame CSS pixels), popup/new-tab adoption, navigation and load waits, dialogs, and crash/detach handling. A middle path exists: chromiumoxide_cdp 0.9.1 is a separate crate and can supply typed command structs over our own transport, with serde_json::Value for events, at the cost of compiling the 5 MB generated file.

## Things the research missed

### Both transports the researcher weighed (port 0 and the pipe) mark the browser as automation-controlled; only an explicit port does not, and then no DevToolsActivePort file is written.

Chromium enables AutomationControlled (navigator.webdriver = true) for --remote-debugging-pipe and for --remote-debugging-port=0, and deliberately not for a specific port number. For an app-owned profile the user logs into, that flag is what bot-detection and some sign-in flows key on, so this is a product decision that must be written down, not a side note. With an explicit port the ws URL has to come from the stderr line 'DevTools listening on ws://...' or GET /json/version, and there is a small bind race when pre-selecting a free port.

Source: chromium main content/child/runtime_features.cc lines 342-344, 385-400; chrome/browser/devtools/remote_debugging_server.cc (output_dir only when port == 0)

### The pipe transport is concretely feasible from Rust on both targets; it is not an open research item.

macOS: Chrome reads fd 3 and writes fd 4, which a pre_exec dup2 or the command-fds crate (0.3.3, 2026-04-10) provides. Windows: create two anonymous pipes with inheritable handles and pass `--remote-debugging-pipe --remote-debugging-io-pipes=<read handle>,<write handle>`; Chromium adopts them with AdoptHandle. Framing is NUL-terminated JSON. This removes the unauthenticated loopback port entirely, at the cost described above (navigator.webdriver true).

Source: chromium main content/public/common/content_switches.cc lines 592-596, 969-972; content/browser/devtools/devtools_agent_host_impl.cc lines 109-134, 222-234; crates.io command-fds

### The proposed 'short window after an agent action' rule for holding non-GET requests is not a security boundary.

In the prompt-injection threat model the page is the adversary, and a page can defer its POST with a timer until the window has closed, or submit via script long after the agent typed. The gate should hold every Document-type non-GET request and every formSubmissionGet/formSubmissionPost navigation unconditionally, and treat XHR/fetch/Ping gating as an explicit per-origin policy (ask once, allow-list, or strict) rather than a timing heuristic. The research also has no URL policy: an agent-driven browser can be steered to file:// URLs, chrome:// pages, and loopback services including the app's own llama-server port, and it has no download policy (Browser.setDownloadBehavior with an app-owned directory or deny).

Source: Reasoning from the researcher's own gate design; devtools-protocol Browser.pdl lines 139-156, Page.pdl lines 497-515, 1433-1444

### On macOS 14+ ScreenCaptureKit should be the primary capture path, and the Rust crate choice for it has build consequences the research did not mention.

`screencapturekit` 11.1.2 builds a Swift bridge with `xcrun swift build` (needs the Xcode toolchain on every macOS build machine and CI runner) and bakes in rpaths to /usr/lib/swift and the Xcode toolchain directory. `objc2-screen-capture-kit` 0.3.2 (2025-10-04, 1.1M recent downloads) is a pure-Rust binding in the same objc2 0.3.x family xcap already uses and needs no Swift. Either way SCScreenshotManager is 14.0+, so macOS 13 keeps the CGWindowListCreateImage path. Switching to ScreenCaptureKit does not remove the monthly re-consent prompt on macOS 15+ unless the system picker is used, which does not fit an agent.

Source: screencapturekit-11.1.2/build.rs lines 57, 70, 184-331 and README lines 426-430; crates.io objc2-screen-capture-kit; chromium ui/snapshot/snapshot_mac.mm; press coverage of the Sequoia prompt (9to5mac/TidBITS, 2024)

### Model files cannot be stored or identified by file name alone.

H Company's official repos use generic names: Holo4-35B-A3B-GGUF, Holo4-27B-GGUF and Holo-3.1-35B-A3B-GGUF all contain `q4_k_m.gguf` and `mmproj.f16.gguf`. Four different mmproj naming schemes are in use (`mmproj-<model>-f16.gguf` at ggml-org/bartowski, `mmproj-F16.gguf` at unsloth, `<model>.mmproj-f16.gguf` at mradermacher, `mmproj.f16.gguf` at Hcompany). The downloader must key storage by repo id, detect the projector by the substring 'mmproj', and record the main-file/projector pairing in the registry. Some repos have no projector at all (Mungert/UI-TARS-1.5-7B-GGUF).

Source: Hugging Face API /api/models/<repo>?blobs=true for the repos named

### Realistic step latency for the recommended large grounder is far below interactive speed.

H Company publishes 'Requests per minute' for Holo3.1 35B-A3B inside its own agent: 3.6 on a MacBook M4 Pro with Q4 llama.cpp (about 17 s per step), 9.5 on a DGX Spark. Their tuned recipe uses --ctx-size 65536, q8_0 KV cache, --ctx-checkpoints 8 and --cache-ram 32768. The computer-use loop, its progress UI, the stop control and the hold/drag watchdog timings all need to be designed around 15-20 s per action on a 36 GB Mac, and much less capable models on 16 GB machines.

Source: https://hub.hcompany.ai/models-api/local-inference.md (tables 'Pick a setup' and 'Agent speed in the Holo CLI')

### A text-first route for OS-level control exists and was not considered.

The brief asked about screenshots and vision grounding, but the same accessibility-tree idea chosen for the browser applies to native apps: Windows UI Automation via `uiautomation` 0.25.1 (2026-09-04, Apache-2.0) and macOS AXUIElement via `objc2-application-services` 0.3.2 or `accessibility` 0.2.0. It works with non-vision local models, costs far fewer tokens than 1-2.7k per screenshot, and avoids coordinate conventions entirely for standard controls. macOS already requires the Accessibility grant for input, so no extra permission is needed. At minimum the tool interface should leave room for element-ref actions next to pixel actions.

Source: crates.io API for uiautomation, objc2-application-services, accessibility (versions and dates checked today)

### Screenshots contain the app's own windows and never contain the mouse cursor.

xcap's macOS monitor capture uses OptionAll with window id 0, and its Windows GDI and WGC paths exclude the cursor (WGC explicitly disables it). The always-on-top stop button the researcher recommends, and the chat window itself, will be in every screenshot and can cover targets or be clicked by the model. The architecture needs a rule: hide or exclude the app's windows during capture (Tauri's content-protection setting or minimise), and draw a cursor marker into the image if the model is expected to reason about pointer position. On Windows 10 the WGC path also shows a capture border, so GDI should stay the default there.

Source: xcap-0.9.10/src/macos/impl_monitor.rs line 208, src/windows/wgc.rs lines 159-167

### enigo's crates.io release and its main branch differ on exactly the bugs that matter here.

0.6.1 can crash on macOS when the keyboard layout is read off the main thread and miscomputes coordinates in non-DPI-aware Windows processes; both are fixed on main but unreleased, and main needs Rust 1.93.1. The plan must pick one: pin a git revision of main, or use 0.6.1 and marshal every enigo call (including construction) onto the main thread through Tauri. Neither version tracks mouse buttons or uses VIRTUALDESK, so the own SendInput mouse path and own pressed-set are needed regardless.

Source: raw.githubusercontent.com/enigo-rs/enigo/main/CHANGES.md ('Unreleased' section) and Cargo.toml (rust-version 1.93.1)

### xcap drags heavy Linux system dependencies into any Linux build of the workspace.

xcap's Linux target depends on pipewire 0.10, ashpd, libwayshot-xcap and xcb. Linux is not a shipping target, but if CI runs cargo check/clippy/test on a Linux runner (this repository's own dev environment is Linux) those need libpipewire and xcb development packages. Declare xcap, enigo and the capture/input module under `cfg(any(windows, target_os = "macos"))` target dependencies and stub the traits elsewhere.

Source: xcap-0.9.10/Cargo.toml target.'cfg(all(target_os = "linux", ...))' dependency tables

### Browser vision clicks need their own coordinate mapping, separate from the OS-level one.

Input.dispatchMouseEvent takes CSS pixels relative to the main frame viewport, while Page.captureScreenshot returns device pixels on HiDPI displays (2x on Retina, 1.25-1.5x on scaled Windows displays). When a vision model clicks on a browser screenshot the result must be divided by devicePixelRatio (or the screenshot captured with a clip scale that yields CSS-pixel size) before dispatch, in addition to the model's own 0-1000 or resized-pixel conversion. The research's mapping section covers only OS-level capture.

Source: devtools-protocol Input.pdl lines 173-177; Page.pdl captureScreenshot clip/scale (lines 460, 593-597)

### The DPI fix should be the manifest, and it also applies to any helper process.

The research offers 'after the event loop exists or a custom manifest' as equals. Process DPI awareness set by API is order-dependent and only covers the Tauri process. If capture or SendInput ever runs in a helper or sidecar process (for example a bundled MCP server binary), that process gets no awareness from tao at all. A PerMonitorV2 `dpiAwareness` entry in a custom manifest passed through tauri_build::WindowsAttributes::app_manifest (keeping the Common-Controls 6.0.0.0 dependency from the default manifest) removes the ordering problem; helpers need their own manifest or an explicit SetProcessDpiAwarenessContext call first thing in main.

Source: tao-0.37.2/src/platform_impl/windows/event_loop.rs lines 184-185; tauri-build-2.7.4/src/lib.rs lines 344-451 and src/windows-app-manifest.xml

## Final recommendations

- Record the CDP transport as an explicit decision in ARCHITECTURE.md with its trade-off. Option A, explicit port: pre-select a free loopback port, pass `--remote-debugging-port=<n>` with the app-owned `--user-data-dir`, read the ws URL from the stderr line 'DevTools listening on ws://...' or GET /json/version; navigator.webdriver stays false but the port is unauthenticated. Option B, pipe: `--remote-debugging-pipe` (fds 3/4 on macOS; inheritable handles plus `--remote-debugging-io-pipes=<in>,<out>` on Windows); no listening port, but navigator.webdriver is true. Port 0 plus DevToolsActivePort gives the downside of both (unauthenticated port and webdriver true) and should not be the default. My suggestion: pipe by default because it closes the local-attach hole, with the explicit-port mode as a documented user setting for sites that reject automated browsers.
- Keep the in-house CDP client on tokio-tungstenite 0.30.0 (or a pipe reader/writer for option B) but scope it as a lifecycle component: flat sessions, recursive Target.setAutoAttach with waitForDebuggerOnStart and Runtime.runIfWaitingForDebugger, one session per out-of-process iframe, per-session Fetch.enable and Accessibility.getFullAXTree, popup adoption, navigation waits, and guaranteed resolution of paused requests on stop or crash. Do not justify it by the dropped-event argument alone; the gate-critical types have not changed between r1566079 and r1734725. If time is short, chromiumoxide 0.9.1 via Browser::connect_with_config with ignore_https_errors false, viewport None, ignore_invalid_messages false and a long request_timeout remains a valid fallback behind the same trait.
- Redefine the form-submission gate so no part of it depends on timing. Always hold non-GET requests of resource type Document and all formSubmissionGet/formSubmissionPost navigations until approved. Make XHR/Fetch/Ping gating a per-origin policy (strict, ask once per origin, or allow-list). Add a URL policy enforced in the navigate tool and in the Fetch handler: block file:, chrome: and devtools: schemes and loopback/private addresses by default, with the app's own llama-server and MCP ports always blocked. Set Browser.setDownloadBehavior to an app-owned directory or deny. Describe the whole thing as confirmation UX plus defence in depth, and keep the researcher's list of gaps.
- On macOS make ScreenCaptureKit (SCScreenshotManager) the primary capture path for 14+ and use xcap's CGWindowListCreateImage only on macOS 13. Prefer `objc2-screen-capture-kit` 0.3.2 if the team wants no Swift toolchain in the build; choose `screencapturekit` 11.1.2 only if its higher-level API is worth the Xcode dependency. Test full-display capture with permission granted on macOS 15, 26 and 27 before fixing the fallback order, because permission-less CGWindowList capture already returns nothing on 26 and gray images on 27.
- Use xcap for Windows capture (GDI default; do not enable `wgc` for Windows 10 users because of the capture border). Pin it exactly and smoke-test before adopting 0.9.10, which is one day old; 0.9.8 is the conservative pin. Declare xcap and enigo as Windows/macOS-only target dependencies so Linux CI does not need pipewire and xcb.
- For input, decide between a pinned git revision of enigo main (fixes the off-main-thread macOS crash and non-DPI-aware Windows coordinates, needs Rust 1.93.1) and enigo 0.6.1 with every call marshalled to the main thread. In both cases construct it lazily with open_prompt_to_get_permissions false, implement Windows mouse move and buttons directly with SendInput using MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK, keep our own pressed-set for keys and buttons, and tag injected events (enigo's EVENT_MARKER / event_source_user_data) so real user input can be told apart and can pause the agent.
- Set DPI awareness in a custom Windows manifest (PerMonitorV2, keeping the Common-Controls 6.0.0.0 dependency) via tauri_build::WindowsAttributes::app_manifest instead of relying on call ordering after tao's event loop. Run capture and input in the main Tauri process; if any helper process ever does either, give it the same manifest. On macOS the same rule keeps TCC attribution on the signed app bundle.
- Key the model registry by Hugging Face repo id, not by lineage. Each entry carries: main GGUF file, mmproj file, coordinate_mode (absolute_resized, norm_1000_xy, norm_1000_box with explicit axis order), smart_resize factor, required --image-min-tokens, licence, and a 'convention verified' flag. Ship as verified only what a primary source documents: Qwen3-VL (0-1000, factor 32, official Apache-2.0 GGUF with mmproj), Holo-3.1 and Holo4-35B-A3B (0-1000 JSON, Apache-2.0), UI-TARS-1.5 and Fara-7B (absolute resized pixels, factor 28). Mark Holo2, Holo1.5, Qwen3.5, Gemma 4 axis order, UI-Venus-2, Fara1.5 and OS-Atlas as unverified and require the one-click calibration test before enabling them. Do not offer Holo4-27B (CC-BY-NC) or UI-Venus-2 (licence pending despite the apache-2.0 tag on the bartowski GGUF) as defaults.
- Store downloaded models under a repo-qualified path and detect projectors by the substring 'mmproj', because official Holo repos all use `q4_k_m.gguf` and `mmproj.f16.gguf`. Refuse to enable vision or computer-use tools for a model whose projector is missing. Always pre-resize screenshots to the exact smart-resize size, start llama-server with --image-min-tokens 1024 for Qwen-family grounders (it is a launch flag, so the model registry drives server restarts), send images only as data URIs, and use llama-server's `response_format` json_schema plus `chat_template_kwargs: {enable_thinking: false}` for localisation calls.
- Design the computer-use loop for slow steps: about 17 s per action for the 21.3 GB Holo model on an M4 Pro per H Company's own numbers. Keep only the latest one or two screenshots in context, show per-step progress, make stop instantaneous and independent of the model call, and put time limits on any held key, button or drag. Hide or exclude the app's own windows and the stop overlay from captures, and draw a cursor marker when the model needs pointer position.
- Leave an interface seam for element-ref actions at OS level (Windows UI Automation via `uiautomation` 0.25.1, macOS AXUIElement) next to pixel actions, mirroring the browser's ref-based snapshot. It is the only OS-level path that works with non-vision local models and it is far cheaper in tokens; it can be a later milestone, but the tool schema should not assume pixels only.
- Keep the researcher's macOS permission flow (preflight, request on explicit click, poll, restart button for Screen Recording, one stable signing identity for every build) with two changes: treat the System Settings deep links as best-effort with a written manual path as fallback, since they remain unverified on macOS 26 and 27, and word the 26.1 issue correctly as a Settings-list bug that Apple DTS acknowledged, not as a rule that only bundles may capture.
- Items still unverified after this review and needing a real-machine test before release: Edge's behaviour for the default-profile restriction, the deep links on macOS 15/26/27, full-display CGWindowListCreateImage with permission on macOS 26/27, the App Paths\msedge.exe registry key, uiAccess requirements, and the coordinate conventions listed as unverified above. Evidence I collected is under <temp workspace> (crates, chromium, llama, pdl, pw, npm, docs, git); nothing was written to the repository.

One small correction to item (i): Windows detection is not registry-only. detection.rs first honours a `CHROME` environment variable, then a PATH lookup (`which chrome`, `msedge`, ...), then App Paths\chrome.exe (HKLM, then HKCU), then the single hard-coded Edge x86 path. An env-var/PATH-driven executable choice is another reason to write our own detector.
- chromiumoxide typed events can be silently dropped when the browser is newer than the pinned protocol (closed enums, ignore_invalid_events default true), which would hang a Fetch-based gate. — Mechanism confirmed: cdp.rs is 5,189,142 bytes / 111,037 lines with zero `serde(other)`; network::ResourceType has 19 closed variants; InvalidMessage is swallowed when ignore_invalid_messages is true.
