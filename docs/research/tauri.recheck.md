### `bundle.windows.bundleVCRuntime: true` is useful if llama.cpp binaries are not statically linked against the VC runtime

Status: corrected

It is required, and it does not work as-is with the recommended layout. Upstream llama-server.exe, llama-server-impl.dll, llama.dll and ggml-*.dll import VCRUNTIME140.dll, VCRUNTIME140_1.dll and MSVCP140.dll, and the zip does not contain them. bundleVCRuntime copies those DLLs to the install root ('alongside the application'). A sidecar in `llama/<variant>/` started with cwd set to its own folder does not search the install root. Either copy the VC runtime DLLs into the llama folder as resources, or add the install root to the child's PATH. GitHub runners and dev machines have the redistributable installed, so this only fails on clean user machines; whether a clean Windows 10/11 already has these DLLs was not tested.

## Things the research missed

### On Windows the NSIS updater cannot replace llama-server files while a llama-server process from the install directory is still running, and nothing in Tauri stops it

The installer's running-app check (Restart Manager) covers only `$INSTDIR\<main>.exe`; resources and sidecars are then overwritten with plain `File` instructions. The updater's Windows install path runs `on_before_exit` (default `cleanup_before_exit`, which clears trays and resource tables but kills no child processes), launches the installer, then calls `std::process::exit(0)`, so destructors and tokio `kill_on_drop` never run. A live llama-server.exe and its ~30 loaded DLLs stay locked, giving a failed or half-applied update. Design for it: stop the sidecar explicitly before `Update::install`, register it in the updater's `on_before_exit`, put it in a Windows Job Object with kill-on-close as a backstop, and add an NSIS_HOOK_PREINSTALL step that kills stray llama-server.exe under $INSTDIR (orphans left by a crash hit the same lock). Behaviour of the overwrite failure in passive mode was not tested.

Source: tauri@tauri-v2.12.5 crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi (L690-706) and utils.nsh (L23-72) ; plugins-workspace@v2 plugins/updater/src/updater.rs (L1009-1050) ; tauri crates/tauri/src/app.rs (L1126-1140)

### The shape of current upstream llama.cpp release artifacts changes the packaging plan

Checked on release b12242. Windows: llama-server.exe is a 9.7 KB stub; the code is in llama-server-impl.dll (10 MB) plus llama-common.dll, llama.dll, mtmd.dll, ggml.dll, ggml-base.dll, 14 ggml-cpu-*.dll variants, ggml-rpc.dll and libomp.dll; nothing is Authenticode-signed; the VC++ runtime is imported but not shipped. macOS arm64: same stub-plus-dylib structure, minos 13.3, distributed as .tar.gz with versioned dylibs and symlinks. The zips also carry about 20 unrelated tools (llama-connect.exe alone is 11 MB) that should be pruned. The fetch script therefore has to select files, fix the macOS rpath and add the VC runtime, and the architecture should record a pinned llama.cpp build tag with per-file hashes.

Source: https://github.com/ggml-org/llama.cpp/releases/download/b12242/ : llama-b12242-bin-win-cpu-x64.zip, -win-vulkan-x64.zip, -bin-macos-arm64.tar.gz (inspected locally)

### Ad-hoc macOS signing is not a workable placeholder for the computer-use feature

macOS privacy grants (Accessibility, Screen Recording) are tied to the app's designated requirement. An Apple engineer states on the developer forums that ad-hoc signing gives no stable designated requirement, so version N+1 is not recognised as the same code and the grants are lost after every update. With a Developer ID certificate the requirement is stable. Ad-hoc signing plus the default hardened runtime is also likely to refuse the 10 ad-hoc-signed llama dylibs (library validation), so the ad-hoc phase needs `hardenedRuntime: false`; that part is untested. Budget for the Apple Developer Program before shipping computer use or auto-update on macOS.

Source: https://developer.apple.com/forums/thread/795739 (via web search) ; tauri@tauri-v2.12.5 crates/tauri-bundler/src/bundle/settings.rs L363

### Azure Artifact Signing may not be available to this project at all

Microsoft's documentation limits Public Trust identity validation to organizations in the USA, Canada, EU and UK, and to individual developers in the USA and Canada only. Community reports from March 2026 say individual onboarding elsewhere is not possible. If the publisher does not qualify, the Windows plan needs another route through the same generic `signCommand` hook (an OV certificate on a cloud HSM or key vault, or a signing service for open-source projects). I read this from search summaries of Microsoft Learn pages, not the pages themselves.

Source: https://learn.microsoft.com/azure/artifact-signing/quickstart ; https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options (via web search)

### Tool approval needs its own trusted surface, enforced with the capability system

The researcher says to enforce approvals in Rust, but an XSS in the chat window (which renders model output) can call the same `approve_*` command the UI calls. Because AppManifest makes app commands per-window, the approval commands can be granted only to a dedicated `approval` window (or replaced by native dialogs raised from Rust through the dialog plugin) that never renders model or tool output. The chat window then cannot approve its own tool calls even if compromised. This is a third capability file alongside main and overlay.

Source: tauri@tauri-v2.12.5 crates/tauri/src/webview/mod.rs (L2051-2109) ; tauri-docs@v2 security/capabilities.mdx (L188-210)

### macOS GUI apps do not inherit the user's shell PATH, which breaks terminal, git and MCP tools

An app launched from Finder or the Dock gets a minimal PATH, so `git`, `npx`, `uvx`, Homebrew binaries and user-configured MCP server commands are not found by `Command::new`. Tauri maintains fix-path-env-rs for this (it reads the login shell configuration); it is a git-only dependency, not on crates.io, so pin it by revision or implement the same lookup. On Windows, npm-style shims are `.cmd` files that `Command::new("npx")` does not resolve; that part is from general Rust knowledge and was not re-tested here.

Source: https://github.com/tauri-apps/fix-path-env-rs (README on dev branch) ; https://crates.io/api/v1/crates/fix-path-env (does not exist)

### The updater holds the entire installer in memory and has no delta or resume, so installer size is a recurring cost

`Update::download` appends every chunk to one Vec<u8> and verifies it afterwards. Every bundled megabyte of llama.cpp is re-downloaded and held in RAM on each update. This supports one pruned Vulkan-capable backend in the installer (roughly 30-40 MB compressed) and everything else, CUDA in particular, as a separately versioned download keyed to the bundled llama.cpp build tag.

Source: plugins-workspace@v2 plugins/updater/src/updater.rs (L819-895)

### A CUDA backend downloaded at run time is unsigned code and needs its own trust and compatibility rules

Upstream binaries carry no Authenticode signature, and Tauri's docs say Windows 11 Smart App Control blocks unknown unsigned apps with no per-app override, so an on-demand upstream CUDA build is expected to be blocked on those machines (not tested). The pack must also match the bundled llama.cpp build exactly, since ggml-cuda.dll loads against the bundled ggml-base.dll. Re-host the pack, sign it in CI if a certificate exists, pin SHA-256 hashes in the app, and re-fetch after any app update that changes the llama.cpp tag.

Source: tauri-docs@v2 distribute/Sign/windows.mdx L14 ; llama-b12242-bin-win-cpu-x64.zip (no Authenticode directories)

### latest.json can silently lose a platform when matrix jobs finish close together

Each job reads the existing latest.json, merges its own keys, deletes the old asset and uploads a new one, with no locking. If the Windows and macOS jobs overlap in that window, the later upload replaces the earlier job's entries and that platform's users see no update. Since the release is a draft, add a final job that downloads latest.json and fails unless both `windows-x86_64` and `darwin-aarch64` keys are present, before anyone publishes the draft.

Source: tauri-action@v1 src/upload-version-json.ts (L57-99, L277-300) ; src/upload-release-assets.ts (L29-66) ; src/index.ts (L131-146)

### Downloaded models should not live under the identifier directories that the uninstaller can wipe, and Tauri 2.12 has a config for this

The NSIS 'delete app data' checkbox removes %APPDATA%\<identifier> and %LOCALAPPDATA%\<identifier>, which is where `app_data_dir` and `app_local_data_dir` point. Put multi-GB models in a user-visible, user-configurable models directory outside those paths; `app > appDirectoriesOverride` (new in 2.12.0) can relocate the Tauri-managed directories if needed. The researcher listed the risk but gave no placement decision.

Source: tauri@tauri-v2.12.5 nsis/installer.nsi (L915-929) ; crates/tauri/CHANGELOG.md (2.12.0, #14620)

### 'No telemetry' needs scoping because WebView2 is a Microsoft component with its own network behaviour

wry starts WebView2 with `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection` by default, so SmartScreen URL checks are off unless the app sets `additionalBrowserArgs` (which replaces the defaults and must then repeat them). The Evergreen runtime still updates itself through Edge Update outside the app's control. State the guarantee as 'the app makes no network requests except user-initiated model downloads and opt-in update checks'. WebView2's own diagnostic data behaviour was not verified.

Source: wry@wry-v0.57.1 src/webview2/mod.rs L311 ; tauri@tauri-v2.12.5 crates/tauri-utils/src/config.rs (L2129-2135)

### Sidecar orphans after a crash are not handled on macOS

`kill_on_drop` and RunEvent::Exit cleanup do not run when the app crashes or is force-quit. A Windows Job Object covers that platform; macOS has no equivalent, so a crashed app leaves llama-server holding several GB of RAM and its port. Record the child PID and port in a state file and kill a stale instance at startup, and use a random port so a leftover process cannot be mistaken for the new one.

Source: plugins-workspace@v2 plugins/shell/src/lib.rs (L163-164, cleanup only on RunEvent::Exit) ; general process semantics, not tested

## Final recommendations

- Scope of this review: I checked registries, read Tauri, plugin, tao, wry and tauri-action source at the stated tags, and inspected the actual llama.cpp b12242 release archives. Nothing was built or run, and no file in the repository was touched. Clones and downloads are under <temp workspace>
- Keep the researcher's version pins: tauri 2.12 (2.12.5), tauri-build 2.7, @tauri-apps/cli and api ^2.12, plugins on their 2.x lines, rust-version 1.90. Commit Cargo.lock and the npm lockfile, and never copy versions from `cargo search` or npm `next`, which show 3.0.0-alpha.
- Windows packaging: ship one llama folder through `bundle.resources` built from the upstream Vulkan zip, pruned to llama-server.exe, llama-server-impl.dll, llama-common.dll, llama.dll, mtmd.dll, the ggml*.dll files and libomp.dll. Do not ship a separate CPU variant unless testing on a machine without Vulkan shows the fallback fails.
- Windows VC++ runtime: put VCRUNTIME140.dll, VCRUNTIME140_1.dll and MSVCP140.dll in the same folder as llama-server.exe (or add the install root to the child's PATH if you use bundleVCRuntime). Test the installer on a clean Windows VM, because CI runners and dev machines hide this failure.
- macOS packaging: choose explicitly between (a) upstream tarball with llama-server as externalBin, the 10 dylibs in bundle.macOS.frameworks and an added rpath `@executable_path/../Frameworks`, or (b) your own static llama.cpp build as a single externalBin. Set minimumSystemVersion to "13.3" for (a); 13.0 is only reachable with (b).
- Sidecar lifecycle must be an architecture section, not an implementation detail: Job Object with kill-on-close on Windows, process group on macOS, explicit shutdown before `Update::install` and in the updater's on_before_exit hook, cleanup on RunEvent::Exit, an NSIS pre-install hook that kills stray llama-server.exe, and stale-PID cleanup at startup.
- Capabilities: declare every app command with `tauri_build::AppManifest::commands`, list capability files explicitly, and use three windows/capabilities (main, overlay, approval). Grant approval commands only to the approval surface or use native dialogs from Rust, so the window that renders model output cannot approve tool calls.
- Keep the proposed CSP, navigation handlers and Channel-based streaming as written; they hold up against the source. Test CSP only in `tauri build --debug`, since desktop dev mode bypasses it. Grant `dialog:allow-message` rather than the deprecated ask/confirm aliases.
- Updater: Rust-only check behind an explicit user action, no `updater:*` permission in any capability, `requireSignedVersion: true` from the first release, key generated and backed up now. Decide whether to rewrite latest.json URLs from api.github.com to github.com release-download URLs; I could not test the rate-limit risk.
- CI: tauri-apps/tauri-action@v1 with `--bundles nsis` on Windows and `--target aarch64-apple-darwin --bundles app,dmg` on macOS; pin runner images instead of `-latest`; use `args: --no-sign` for PR builds; export APPLE_* and signing variables only when the secrets are non-empty; add a final job that checks latest.json contains both platform keys before the draft is published.
- Signing: confirm Azure Artifact Signing eligibility for the publisher's country and entity type before designing around it, and keep signing behind `signCommand` in a separate config file so the provider can change. On macOS, treat a Developer ID certificate as a prerequisite for computer use and auto-update; use ad-hoc signing with `hardenedRuntime: false` only for internal builds.
- Installer and data: NSIS `currentUser`, `embedBootstrapper` for WebView2 (switch to `offlineInstaller` only if offline first install is promised), CUDA as a separately versioned, hash-pinned download tied to the bundled llama.cpp tag, and models stored in a user-configurable directory outside the identifier folders the uninstaller can delete.
- Add PATH resolution for macOS GUI launches (fix-path-env-rs pinned by revision, or an equivalent) to the design of the terminal, git and MCP tools.
- Linux dev in this container works as the researcher described: `apt-get update && apt-get install -y libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev libxdo-dev`, keep llama resources in the per-platform config files, and use xvfb-run for anything that opens a window.

Once it exists, every app command needs a generated `allow-<command>` in some capability, so all commands must be listed. Docs confirm the boundary is the window label and that explicitly listed capabilities replace auto-enabling.

The hint that hardenedRuntime=false helps ad-hoc signing is a doc comment in tauri-bundler settings.rs (L363), not on the docs site.

The upstream llama.cpp Windows binaries are all unsigned (no Authenticode directory in any of the 52 files I checked), so each bundled exe/dll costs one signing call per build.
- Spawning from Rust with std/tokio process needs no plugin and no capability; tauri-plugin-shell only adds path resolution and CREATE_NO_WINDOW; shell 2.6.0 added kill_on_drop and 2.5.0 added processGroup — Confirmed in the shell plugin source and changelog. Caveat the researcher did not draw out: `kill_on_drop(true)` does not fire when the process ends through `std::process::exit`, which is exactly how the updater exits on Windows (see missed items). Registering the shell plugin with no `shell:*` permission in any capability would also give the webview zero spawn surface, so 'no plugin' is a preference, not a security requirement.
- CSP is only applied to assets served by Tauri's protocol; on desktop `tauri dev` with a dev server it is not applied; Tauri appends 'self', nonces and hashes to script-src/style-src — PROXY_DEV_SERVER is `cfg!(all(dev, mobile))`; on desktop dev the webview loads devUrl directly and the CSP header is only added in `get_asset` for .html assets. The config doc comment saying csp 'is also injected on dev' is therefore misleading for desktop. Style nonces are only injected for `<style>` elements, script nonces only for `script[src^='http']`.
- Tauri does not block navigation to remote URLs by default; on_navigation / on_new_window handlers must be added; windows need `create: false` plus WebviewWindowBuilder::from_config to attach them — The internal handler only calls the user's handler and plugin hooks, otherwise returns true. `from_config`, `on_navigation`, `on_new_window` exist, as do `on_download` and `on_permission_request` (new wry permission handler API in 2.12.0), which the researcher did not mention.
- Use tauri::ipc::Channel for token streaming; JSON under 8192 bytes (raw under 1024) is delivered by direct eval; events are documented as unsuitable for high throughput — Constants MAX_JSON_DIRECT_EXECUTE_THRESHOLD = 8192 and MAX_RAW_DIRECT_EXECUTE_THRESHOLD = 1024; docs wording matches. The 2.12.3 fix (delivery continues after an onmessage handler throws) is in the changelog.
- Overlay: macOSPrivateApi is a no-op since 2.12.1; click-through is runtime-only (WS_EX_TRANSPARENT|WS_EX_LAYERED on Windows); focusable:false is WS_EX_NOACTIVATE; macOS alwaysOnTop is NSFloatingWindowLevel and visibleOnAllWorkspaces only sets CanJoinAllSpaces — All confirmed in tauri config docs/changelog and tao 0.37.2 source. On macOS `focusable:false` maps to canBecomeKeyWindow returning false. tauri-nspanel 2.1.1 exists on crates.io.

Config fields and defaults match config.rs; endpoints must be https in release builds. `Update::install` calls `verify` first. Additional facts from the same file: the whole update is buffered in a Vec<u8> in memory, there are no delta updates, and the default permission set grants all four commands.
