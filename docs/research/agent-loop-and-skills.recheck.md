### MCP error handling: tool execution errors return isError:true; 'unknown tool and invalid arguments are JSON-RPC errors (-32602)' (cited from spec 2025-06-18)

Status: corrected

The citation is two revisions old; the current revision is 2026-07-28 and rmcp 3.9.0 sets LATEST to it. Since 2025-11-25, input validation errors are tool execution errors (`isError: true`) that clients SHOULD pass to the model. Only unknown tool, malformed request and server errors are JSON-RPC errors, which clients MAY pass on. The opencode repair plugin and Cline's maxConsecutiveMistakes default of 6 in the same finding are correct.

### Recommendation: pin the conversation with id_slot and run -np 2 with a second slot for side requests, because 'a summarization request on the same slot invalidates the conversation's KV cache'

Status: corrected

Wrong for current master on two counts. (1) Explicit -np N leaves kv_unified false, so per-slot context becomes n_ctx / N: `-c 32768 -np 2` gives two 16k slots. (2) With the defaults (auto 4 slots, unified KV, --cache-idle-slots on, --cache-ram 8192), idle slots are saved to a host-RAM prompt cache and cleared when another task starts, then restored on a prefix match. Slot choice is by prompt similarity (-sps 0.10), so id_slot pinning is optional. The better setup is to leave -np unset, or use -np N with --kv-unified, and size --cache-ram deliberately.

## Things the research missed

### Sidecar tool arguments are grammar-constrained, and third-party schemas can break the request

llama-server compiles every tool's `parameters` schema into a GBNF grammar (lazy for tool_choice auto when the template has a trigger marker, eager for required). On the bundled sidecar, malformed or schema-violating arguments are therefore rare; the realistic failures are truncation (finish_reason length), templates with no trigger marker, and remote endpoints. The converter throws 'JSON schema conversion failed' on unresolved `$ref`, invalid `pattern` or nesting over 128 levels, and silently relaxes unsupported patterns. One odd MCP inputSchema can fail every chat request that carries it. The architecture needs a schema down-leveller in Rust before tools go to the sidecar (inline local $defs, drop remote $ref / pattern / format, bound depth), with the full schema still validated in Rust.

Source: llama.cpp @b12242 common/chat-auto-parser-generator.cpp L66-90, L296-310; common/json-schema-to-grammar.cpp L361-425, L716, L1007-1012; common/common.h L34

### The jsonschema crate fetches remote and file $refs by default, which the current MCP spec forbids

jsonschema 0.61.0 has default features resolve-http and resolve-file; its docs say it 'resolves HTTP references using reqwest and file references from the local file system'. MCP tool schemas come from untrusted servers, so this is an SSRF, local-file-read and offline/no-telemetry violation. MCP 2026-07-28 says implementations MUST NOT automatically dereference network `$ref`s, SHOULD reject schemas with unresolved external refs, and SHOULD bound depth, subschema count and validation time. Use `default-features = false` (or `options().offline()` / a refusing Retrieve impl), which also drops the reqwest + rustls + aws-lc-rs build from this path. Bound `pattern` evaluation too, since the crate uses a backtracking regex engine.

Source: cargo info jsonschema; https://docs.rs/jsonschema/0.61.0/jsonschema/ ; https://modelcontextprotocol.io/specification/2026-07-28/basic/index (JSON Schema Usage: $ref Resolution, Composition-Keyword Resource Use)

### The MCP material is based on a stale spec revision; 2026-07-28 changes the client the loop talks to

The current protocol is 2026-07-28 and rmcp 3.9.0 defaults to it. It removes the initialize handshake and sessions (per-request `_meta` protocol version and capabilities, plus `server/discover`). Every result carries `resultType`, and `tools/call` may return `input_required` (elicitation via multi round-trip requests), which the loop must handle by retrying with `inputResponses` and `requestState` instead of treating it as a tool result. Roots, Sampling and Logging are deprecated, and list changes arrive over `subscriptions/listen`. Servers SHOULD return tools in deterministic order, and clients SHOULD prefix tool names per server on collision, which also keeps the prompt prefix stable for the KV cache. Older servers still need the 2025-11-25 handshake path (rmcp `LATEST_WITH_INITIALIZE`).

Source: https://modelcontextprotocol.io/specification/versioning ; /specification/2026-07-28/changelog ; /specification/2026-07-28/server/tools ; rust-sdk @f2b0ddf crates/rmcp/src/model.rs L169-201

### llama-server's default exposure is unsafe for a bundled sidecar and the recommended launch flags do not address it

Defaults: no API key, CORS origins `*` with credentials enabled (the Origin is echoed back), web UI enabled, `/slots` monitoring endpoint enabled. Binding to 127.0.0.1 does not stop a web page in the user's browser, or any local process, from calling the model endpoints. Launch with a per-run random `--api-key` (or `--api-key-file`), `--no-webui`, `--no-slots` and a restrictive `--cors-origins`, in addition to keeping `--tools`, `--agent`, `--mcp-servers-*` and `--ui-mcp-proxy` off. The built-in tool set includes exec_shell_command and write_file.

Source: llama.cpp @b12242 common/common.h L671-701; tools/server/README.md L198-217, L228; tools/server/server-http.cpp L252-290

### llama-server downloads http(s) image URLs itself

`handle_media` fetches any `image_url.url` that starts with `http` (10 MB cap, 10 s timeout); `file://` needs `--media-path`. That code path has no offline check, and `--offline` is only consulted in the model-download code. For an offline app with browser and computer-use tools, the Rust layer must convert every image to a base64 data URI and never forward a model- or tool-supplied URL. The research also does not cover how screenshots get back to the model: image parts are accepted in any role's content array, but whether a template renders them inside a tool message varies, so check with `/apply-template` or send the image in a following user message.

Source: llama.cpp @b12242 tools/server/server-common.cpp L1218-1262, L1286-1300, L1432-1452; common/download.cpp; README L230, L1738

### Context and memory sizing defaults not covered: --fit and --cache-ram

`--fit` is on by default and adjusts unset arguments to device memory; with `-c` unset it may choose a context as small as `--fit-ctx` 4096. Per-slot context is also capped by n_ctx_train and divided by the slot count when KV is not unified. Read the effective value from `GET /props` (`default_generation_settings.n_ctx`) after start instead of assuming the requested one. `--cache-ram` defaults to 8192 MiB of host RAM for saved prompt states, which is large for a 16 GB consumer machine, so set it explicitly; setting it to 0 also disables idle-slot caching.

Source: llama.cpp @b12242 tools/server/README.md L90-92, L169-171; tools/server/server-context.cpp L1444-1470, L1667-1670, L5089-5097

### tool_choice "none" keeps the prompt prefix; removing tools does not

The recommended 'tools-disabled final request' at the step limit, and the summarization call, should send the same `tools` array with `tool_choice:"none"`. In the source the tools are still passed to the template and only the tool parser and grammar are skipped, so the KV-cache prefix should survive; removing `tools` re-renders the prompt head and forces a full re-evaluation, which is slow on local hardware. This is inferred from the code and should be confirmed with `/apply-template`. The same reasoning says to keep the system prompt, skills catalogue and tool order byte-stable across turns.

Source: llama.cpp @b12242 common/chat-auto-parser-generator.cpp L66-76, L126; common/chat.cpp L1486, L1545-1556

### A mid-stream control endpoint exists for ending reasoning

`POST /v1/chat/completions/control` with `{id:<chatcmpl id>, action:"reasoning_end"}` forces the end of thinking on a running completion. Together with `--reasoning-budget` and `reasoning_effort` it is a server-side answer to the listed risk that a reasoning model spends the whole max_tokens budget on thinking. `max_completion_tokens` and `max_tokens` are both aliases of n_predict.

Source: llama.cpp @b12242 tools/server/server.cpp L183; tools/server/server-context.cpp L6070-6092; tools/server/server-schema.cpp L46-49; README L240-241, L1453

### SSE client choice

Given the wire quirks (comment pings, an error object as terminal event, missing [DONE], non-SSE error bodies on the first result, vendor fields such as reasoning_content, timings and prompt_progress), a typed OpenAI client is a poor fit. Use reqwest 0.13 with a small hand-written chat client and a transport-agnostic SSE decoder: eventsource-stream 0.2.3 (old, last published 2022, but very widely used) or sse-stream (0.3.0 current; rmcp requires ^0.2.4, so one of the two versions is already in the tree). async-openai 0.43.0 is maintained but would need its bring-your-own-types route for these fields.

Source: crates.io API (reqwest-eventsource 0.6.0 deps, async-openai 0.43.0 deps, rmcp 3.9.0 deps, sse-stream, eventsource-stream); llama.cpp server-context.cpp L5465-5600

### Third-party Rust Agent Skills crates exist; none is official

crates.io has several small skills-ref ports (turul-agent-skills 0.1.1, skills-ref-rs 0.1.1, skref 1.2.0, agent-skills 0.3.0). None comes from the agentskills organisation and the reference validator is about 150 lines, so the plan to implement it in-house is sound. serde-saphyr is the maintained YAML parser for untrusted frontmatter; mirroring strictyaml exactly means reading every scalar as a string.

## Final recommendations

- Accept the research as the basis for the agent-loop section. The wire shapes, constants, endpoint names and Agent Skills rules all held up against source at today's upstream HEADs. Three things need fixing before ARCHITECTURE.md is written: the MCP error-handling paragraph, the slot recommendation, and the crate list.
- Write the MCP parts against protocol 2026-07-28, which is rmcp 3.9.0's LATEST, with a 2025-11-25 handshake fallback for older servers. Feed `isError:true` results back to the model, including input-validation errors. Treat JSON-RPC errors (unknown tool, malformed request) as loop or host errors that may be summarised to the model. Handle `resultType:"input_required"` from tools/call as a UI elicitation round-trip, not as a tool result. Prefix tool names per server and keep tool order deterministic.
- Run two schema paths in Rust. (a) Validate with `jsonschema = { version = "0.61", default-features = false }`, with no HTTP or file `$ref` resolution, bounded depth, subschema count and time, and rejection of schemas with unresolved external refs. (b) Send the sidecar a down-levelled copy (local $defs inlined, no pattern / format / remote $ref, bounded depth), because llama-server turns tool schemas into a GBNF grammar and fails the request on conversion errors.
- State in the architecture that on the bundled sidecar, tool-call arguments are grammar-constrained by llama.cpp. Order the client-side defences accordingly: handle finish_reason "length", handle the 'does not match the expected ... format' error, then schema validation, then schema-guided repair. The plain-text fallback parser is for remote endpoints only. Keep its exact-name and schema acceptance rule, and add the GLM `<arg_key>/<arg_value>` format to its catalogue.
- Launch llama-server with at least: `--host 127.0.0.1 --port <chosen> --api-key <random per launch> --no-webui --no-slots --cors-origins <restrictive> -c <ctx> --cache-ram <explicit MiB> --no-context-shift`. Never pass `--tools`, `--agent`, `--mcp-servers-*` or `--ui-mcp-proxy`. Always send the Authorization header from Rust.
- Drop the '-np 2 plus id_slot' advice. Leave `-np` unset (auto = 4 slots sharing one unified KV pool), or pass `--kv-unified` with any explicit `-np`. Rely on idle-slot caching into `--cache-ram` for side requests such as titles and summaries, and benchmark restore time and RAM for the target model sizes. Document that explicit `-np N` without unified KV divides the context by N.
- After every sidecar start, read the effective per-slot context from `GET /props` and use that number for budgeting. Do not use the requested `-c` or the GGUF trained length, since `--fit`, n_ctx_train capping and slot division can all change it.
- Send on every sidecar request: `parallel_tool_calls` explicitly, `tool_choice` as a string only ("auto", "none" or "required"; object forms silently become auto), `stream_options.include_usage`, `cache_prompt:true` and `max_tokens`. For the step-limit and summary calls keep the same `tools` array and set `tool_choice:"none"`, after confirming prefix stability with `/apply-template`.
- Build the HTTP client on reqwest 0.13 with a hand-written chat-completions stream reader and a transport-agnostic SSE decoder; do not use reqwest-eventsource 0.6.0. The reader must check the HTTP status before SSE parsing, ignore `:` comment lines, treat `data: {"error":...}` as terminal, tolerate a missing [DONE], accept `choices: []` usage chunks, and read both `reasoning_content` and `reasoning`.
- Token accounting on the sidecar: pre-check with `POST /v1/chat/completions/input_tokens`, falling back to `/apply-template` plus `/tokenize` if the pinned build lacks it. Reconcile with `usage` and `timings`, and treat HTTP 400 `exceed_context_size_error` (with its `n_prompt_tokens` and `n_ctx`) as a forced compaction. On remote endpoints use ceil(chars/3) calibrated from real `usage.prompt_tokens`.
- Remote providers: Ollama via `/api/ps` context_length, with a UI warning at 4k and a pointer to OLLAMA_CONTEXT_LENGTH or a Modelfile num_ctx; LM Studio via `GET /api/v1/models` and optionally `POST /api/v1/models/load {context_length}`; vLLM via `max_model_len` and `/tokenize`. Assume Ollama `/v1` truncates silently and detect it by comparing reported prompt_tokens with the estimate.
- Never pass a URL in `image_url` to the sidecar. Convert screenshots and fetched images to base64 data URIs in Rust. Decide the screenshot-return shape per template (tool-message content part or a following user message) and test it with `/apply-template`.
- Skills: implement strict (skills-ref-equivalent) and lenient (client-guide) validation in-house, parsing frontmatter with serde-saphyr and treating scalars as strings. Advertise with the `<available_skills>` block plus an `activate_skill` tool with an enum name, and omit both when there are no skills. Exempt `<skill_content>` from compaction and gate project-level skills on folder trust.
- Compaction and limits: adopt the researcher's local-model adjustments. Trigger at n_ctx minus max(reply reserve, about 15-20%), cap tool output relative to n_ctx with a head+tail marker and spill-to-file, default 25-50 steps, warn on identical calls at 3 and stop at 5, and allow about 6 consecutive mistakes. Add a reasoning budget (`--reasoning-budget` / `reasoning_effort`, optionally the `/v1/chat/completions/control` reasoning_end action) so thinking cannot consume the whole reply budget.
- Pin the bundled llama-server build (b12242 or later) and add a wire-conformance test that runs on every upgrade. It should cover: a streamed tool call, the usage chunk, the mid-stream error event, the HTTP 400 overflow body, the input_tokens endpoint, `/props` n_ctx, tool_choice none prefix stability, and API-key enforcement. The server's docs and defaults change faster than its documentation, as the port move to 9931 shows.
