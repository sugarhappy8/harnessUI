## How a local model is loaded, configured and reloaded today (0.0.5 items 1 and 2)

The app has only three loading settings, and they apply to every model: a context size, a backend choice (Auto, Vulkan, CUDA, ROCm, Metal or CPU) and a device. All three are stored as one JSON value under the settings key "localModel". Settings → Local models shows only Backend and Context size. Context size is a dropdown with six fixed sizes from 2,048 to 65,536 tokens. Nothing else about loading can be changed: not GPU layers, threads, batch size, flash attention, KV cache type, memory mapping or locking, parallel slots or rope. The launch code fixes those values or leaves llama.cpp's defaults. GPU backends always get "-ngl all". When a model does not fit on the GPU, the app moves it entirely to the CPU instead of splitting it. There is no Reload or Unload button. To reload, you pick the model again from the chat's model list, and that only restarts the server if the context size or a chosen backend has changed. Reloading stops the running server immediately, even if a reply is being written. Shrinking the conversation automatically ("compaction") already exists in the agent loop: it starts at 80% of the budget and runs in three stages. The fit check runs only in the Hugging Face Browse view, uses the global context size and assumes an f16 KV cache. The bundled llama-fit-params tool is found on disk but never run. The model-check profiles in 0.0.4 change only thinking and temperature per model. They are keyed by file name, size and backend, which is a ready pattern for storing settings per model. The pinned llama.cpp build b12110 supports KV cache quantization, flash attention, partial GPU offload and llama.cpp's own fit option, and it serves /v1/messages (Anthropic) and /v1/responses.

### Gaps for the request

- Per-model loading settings do not exist. Needed: a record per model (at least the context size, ideally GPU use, the memory-saving KV cache option and the backend) that is used when that model loads, with the global localModel value as the fallback. It must also work for files opened with 'Open a GGUF file…', which are only in recentLocalModels and not in the models table.
- load_local_model and its four callers (app.ts pickModel, ModelsDialog use, FirstRun importFile, run_diagnostics) send the global settings from the frontend. They need to send just the path and let the backend combine the per-model settings with the global ones in one place. run_diagnostics must use the same function, including the projector lookup, the trained-length cap, set_thinking and the speed check.
- There is no context control at load time and no way to see per model what fits. Needed: a per-model choice ('How much it remembers' / 'Conversation memory') whose options come from the model's trained length and a fit estimate. Optionally 'Largest that fits' through llama-fit-params (-c 0 / --fit-ctx) or through fit::largest_ctx. The catalog recommended_ctx should become the first default for catalog models.
- 'Auto compresses': the conversation part exists (8.4 compaction), but nobody would notice it. The KV cache part is missing: no -ctk/-ctv q8_0 or -fa option, and the fit estimate assumes f16. Verified: q8_0 halves the context memory, 3584 MiB down to 1906 MiB at 32k. If 'auto' means 'pick a context that fits automatically', that is missing too.
- Plain-language settings beyond the context size are missing: GPU use ('As much as fits' = -ngl auto, 'All' = all, 'None' = CPU), 'Keep the model in memory' (-lm mmap+mlock), 'Memory saver' (KV q8_0 with -fa on), maybe 'Speed: threads' (-t). Each needs a typed field in LaunchConfig and build_args, and an update to the args_are_exact test.
- There is no Reload, Apply-and-reload or Unload button. The help text says changes apply 'the next time a model loads', but nothing reloads, and re-picking reloads only when the context size or a chosen backend changed (models_cmd.rs:70-80). Device and any new fields are not compared there. That check would need to compare all launch-relevant fields.
- A reload is not safe while a reply is being written: there is no check of state.generation, and the failure reads 'Could not reach the model server…'. Needed: ask first (or stop the reply cleanly), then reload, with a plain message such as 'The model is restarting with your new settings'.
- Loading status needs plain words: raw stage names ('text model', 'mmproj model'), raw backend and device names ('vulkan · Vulkan1') and step-down text that nests a sentence in parentheses.
- Out of memory always moves the model to the CPU. The message says 'run part of the model on the CPU', but nothing does that. Using -ngl auto (or llama.cpp's own fit) as the GPU default, or as the first retry before the CPU, would deliver it.
- The fit check should take into account the per-model context, the KV cache type and the projector for installed models, and refresh free VRAM when a model is already loaded. Today only the Browse view runs it, with the global context size.
- context_for_defaults (mcp_cmd.rs:966-984) and hub_repo fit_context (hub.rs:283) read the global ctx. With per-model settings they should read the per-model value.

### Risks and constraints

- Security (ARCHITECTURE 7.3, 13.5): llama-server reads LLAMA_ARG_* for every flag and has dangerous flags: --tools, --agent, --connect, --host, --api-key, --media-path, --chat-template-file, --lora, --slot-save-path, --log-prompts-dir, --props. New settings must be typed values from fixed lists added in build_args, never free-text 'extra arguments' or file paths. Keep the environment scrubbing and --offline, --no-slots and --cors-origins none.
- The set_setting allow-list (models_cmd.rs:193-198) blocks unknown keys. Per-model settings need their own validated command, as set_local_model_settings and modelProfile: have.
- Saved-data compatibility: LocalModelSettings has no serde(default). Stored 'localModel' JSON written by 0.0.4 holds only {ctx,backend,device}, and local_model_settings() silently falls back to the defaults when reading fails (settings.rs:58-67, mcp_cmd.rs:977). Every new field needs #[serde(default)], or users silently lose their backend choice. The same applies to any per-model JSON. If you add a table instead, it must be schema V3 in crates/store/src/schema.rs (only V1 and V2 exist, MIGRATIONS at 414).
- Model identity: profile keys include the backend (profile.rs:40-55). A per-model context probably should not depend on the backend, but the GPU-layer count does. Keying by file name and size (or by path) covers picker-opened files that have no row in models. Keying by models.id does not.
- load_tracker compares the whole LocalModelSettings (load_tracker.rs:55), and the 'already loaded' check in models_cmd.rs:70-80 compares only path, n_ctx and backend. New fields must go into both, or a reload with new settings will be skipped or wrongly joined.
- LaunchConfig is built as a struct literal in about 14 places (runtime_manager.rs:398, supervisor.rs:450, server.rs:693-730, launch.rs tests, crates/runtime/tests/llama_server.rs:51). New fields touch all of them. Consider a Default or a constructor. The contract tests (ARCHITECTURE 17) check exact flag spellings on every llama.cpp bump.
- Flag spellings in this build differ from older guides: memory mapping and locking are -lm/--load-mode mmap|mlock|mmap+mlock|dio, and --mlock and --no-mmap do not exist (verified in --help). A quantized V cache generally needs flash attention, and support depends on the backend: Vulkan, ROCm and Metal kernels may differ (inferred, not tested on GPU here).
- Platform differences: Apple silicon uses the Metal working-set limit (fit.rs Target::AppleUnified). Intel Macs use the CPU unless Metal is picked by hand. ROCm must keep HIP_VISIBLE_DEVICES masking. mlock may need privileges or raised limits on Windows and macOS (inferred). On NVIDIA, VRAM overflow can spill silently into system memory, which is what 'Loaded but slow' detects.
- -np 1 and --cache-ram 512 are deliberate for 16 GB machines (ARCHITECTURE 7.3). Item 3 (Claude or Codex talking to the local model) would share this single slot with the app's own chats. More slots split the context (n_ctx per slot = c / np).
- A reload drops the prompt cache, and after the speed check the first turn processes the whole history again, which is slow for long chats. A reload during a turn breaks that turn today.
- The fit check uses free VRAM from a probe cached when the app started. With a model already loaded, the GPU's free memory differs, so 'what fits' for a reload can be wrong unless the app re-probes or subtracts the loaded model (inferred).
- The trained-length cap is silent (models_cmd.rs:59-68): a user who picks 65,536 for a model trained on 32k gets 32k without being told. Per-model choices should be bounded by context_length from the GGUF header. Rope or YaRN extension past that is possible in llama.cpp but should not be exposed to non-technical users.
- Owner wants plain language: the existing English UI copy style is short, concrete and second person (see failure.rs messages). Avoid 'KV cache', 'ngl', 'flash attention' and 'mmap' on screen.

### Suggested approach

1) Add a typed per-model loading settings record, for example LoadSettings {ctx: Option<u32>, gpu: Auto|All|None, memory_saver: bool (-fa on + -ctk/-ctv q8_0), keep_in_memory: bool (-lm mmap+mlock), backend: Option<String>}. Every field gets serde(default). Store it in the settings table under a new prefix such as 'modelLoad:<16 hex of file name + size>', following the profile.rs key pattern, written by its own validated command. Keep 'localModel' as the global default and add serde(default) to LocalModelSettings. 2) Make the backend the single place that resolves settings: load_local_model(path) looks up the per-model record, falls back to the global one, attaches the projector, caps at the trained length and sends the result into RuntimeManager::load. run_diagnostics' reload and every frontend caller go through the same function. 3) Extend LaunchConfig and build_args with typed fields: GpuLayers::Auto for 'as much as fits', -fa, -ctk/-ctv and -lm. Update args_are_exact, the struct literals and the contract test. Consider -ngl auto (llama.cpp fit) as the GPU default or as the first retry before stepping down to the CPU. 4) Fit: actually run llama-fit-params (verified about 0.25 s, no allocation, prints the fitted -c/-ngl and a MiB breakdown) for installed models to offer 'Largest that fits'. Teach fit.rs/summary.rs to count the KV cache at q8_0 (half of f16). Use the catalog recommended_ctx as the first default. 5) UI in plain words: a 'Model settings' panel per model (Installed tab and chat header). It offers 'How much it can remember' (sizes up to the trained length, each marked fits or may not fit), 'Use the graphics card: As much as fits / All of it / Don't use it', 'Save memory (lets it remember more, slightly lower quality)', 'Keep the model loaded in memory', and buttons 'Apply and restart the model' and 'Unload'. ### Open questions

- What does 'auto compresses' mean to the owner: (a) the existing automatic summarising of long chats, which needs only to be visible or explained; (b) shrinking the model's memory use (KV cache q8_0), so a bigger context fits; or (c) automatically picking the largest context that fits the computer? - Which advanced options should appear at all for a non-technical owner? Recommended: context size, GPU use, memory saver and keep-in-memory. Threads, batch size, parallel slots, rope and tensor split stay hidden.
- Should 'run part on the GPU' (-ngl auto / llama.cpp --fit) replace today's all-or-nothing behaviour as the default, given that the out-of-memory message already promises it?
- Should the chat-level context meter offer a one-click 'Give it more memory' that reloads with a larger context when the chat gets close to full?

## Context window size and automatic compression of a conversation (0.0.5 item 1: "allow per model on loading context window setting and it auto compresses")

Automatic compression already exists and runs inside every turn without the user doing anything. Before each model call the loop counts the request. For the local llama-server the count is exact (the /chat/completions/input_tokens endpoint); for remote endpoints it is estimated at 3 characters per token and corrected from usage. When the request passes 80% of the budget, the loop makes room in three stages: (1) all tool results from earlier turns become one-line stubs; (2) the oldest whole turns are summarised by the same model under a fixed template, up to 4 rounds per request; (3) this turn's older tool-call groups are stubbed one at a time, never the latest. If the request still does not fit, the turn fails with "context_full". Summaries go in the `summaries` table, keyed by the last message they cover and limited to their branch, and are sent inside a `<conversation_summary>` block in the system message. The context size is NOT per model. One global setting, `localModel.ctx` (default 8,192; Settings → Local models → "Context size", choices 2,048 to 65,536), is passed as `-c` every time any model loads, capped at the model's trained length. After the load, the app reads the size the server actually allocated from /props, and every turn budgets against that number. Remote endpoints use the size the server reports, asked on every turn, or else one global fallback, `remoteContextLength` (default 4,096). llama-server runs with `--no-context-shift`, so it never drops text by itself: all compression happens in the app. What the user sees of compression is thin. There are passing grey notes during or right after a reply, one of which says "summarised" even when only tool results were shortened. There is no lasting marker in the chat, even though ARCHITECTURE.md 8.4 describes one. The summary text appears only in the Context tab.

### Gaps for the request

- Per-model context size does not exist. There is one global localModel.ctx for every model. Needed: a per-model value stored server-side (for example a settings key such as `modelLoad:<hash of file name+size>` following the evals/profile.rs Identity::key pattern, or a new table or column, which would need a V3 migration in crates/store/src/schema.rs). The global value stays as the default for models without one.
- The load path takes its context from the caller. All three frontend callers (app.ts:396, ModelsDialog.tsx:553, FirstRun.tsx:78) pass the global settings. load_local_model (models_cmd.rs:29) should look up the model's own value itself: per-model → global → capped at trained length → optionally checked against memory with models::fit::check / suggested_ctx (fit.rs).
- No per-model control in the UI where models are loaded (ModelsDialog installed list, the model picker, FirstRun). It needs plain wording instead of 'tokens'/'context', for example 'How much of the conversation this model can keep in mind', with choices sized by trained length and memory, plus a clear 'Apply (reloads the model)' button. Today the only hint is the HF detail line 'Memory estimates assume a context of N tokens.'
- Changing the context needs a reload, because llama-server's -c is fixed at launch. Today a reload happens only by picking the model again, and the setting text says 'Changes apply the next time a model loads.' An explicit reload action is needed that waits for a running reply to finish, plus wording for what happens to the open chat.
- For remote endpoints, only a global fallback (remoteContextLength) exists for models that report nothing. A per-endpoint-model override is missing if 'per model' should cover endpoints too.
- Auto compression exists but is barely visible, and the notes use jargon ('compacting', 'context window', 'tokens'). Needed: stage-specific plain-language notes (the 'compacted' event should carry what happened); a lasting marker in the chat where a summary applies, with a 'Show summary' option (ChatDetailDto does not carry summaries today; latest_summary_on_path is used only by turns.rs and task.rs); and saying when summarising failed (summary_failed is silent).
- Compression runs only lazily, at the start of the next model call that would pass 80% of the budget, so the user waits for an extra summary request before their reply starts. There is no proactive compression after a turn ends or right after a reload to a smaller context, and no 'Compress now' / 'Start fresh from a summary' action. The 80% trigger (TRIGGER_PERCENT) is hard-coded.
- No stage shortens attachments in the current message, or a summary that has grown too large. A large attached document or a big resumed tool result fails with context_full instead of being compressed.
- No handling designed for a context that changes between turns of one chat. The budget is recomputed each turn, but what was stored under the old size (summary, loaded skills, results cut to the old cap) is never resized; see risks.

### Risks and constraints

- Context size changing between turns (reload with a smaller context). The summary is part of the fixed overhead F. It was written under the old size (cap up to 1,024 tokens, 4,096 characters). F (minus pins) is checked against 40% of the new budget in measure() (runner.rs:553-563). On a 4k reload (budget 2,992, tools share 1,196) a large old summary alone can refuse the turn. The refusal names only the tools: 'These N tools need about X tokens; this model's window is 4,096. Turn some tool groups off or raise the context size.' (tool_tokens leaves out the summary). tool_select::other_fixed (tool_select.rs:356-379) does not count the summary either. INFERRED from code, not run.
- A too-large stored summary is never shrunk again: summarise() returns false when no unsummarised earlier messages remain (runner.rs:726-729), so it stays until the user starts a new chat. INFERRED.
- Loaded skills stay in the system message per chat (skills.rs loaded_in). They were admitted against 30% of the context at the time they were loaded (skills.rs:751-752). After a shrink they can push F over the tools' share in the same way. INFERRED.
- Tool results stored under a larger context were cut to the old per-result cap (up to 8,000 tokens). In earlier turns stage 1 stubs them, but a resumed, interrupted turn keeps them in the current turn, and stage 3 never stubs the latest group, so context_full is possible. Mentions are cut at send time to the n_ctx of that moment. INFERRED.
- Chats without their own tool choice switch tools when the size changes: the browser default is on only at >= 8,192 (mcp_cmd.rs Selection::Defaults). The tool-selection allowance shrinks too. Expected, but it can surprise the owner.
- The header meter compares the last stored message's prompt tokens with the current runtime nCtx (ChatView.tsx:139-149). After a shrink it can read 100% (red) until the next reply. A larger context does not bring back summarised messages; summaries are permanent per branch.
- The models_cmd.rs no-op check `current.n_ctx == Some(settings.ctx)` assumes llama-server allocates exactly what -c asked for. If it ever pads the size, picking the model would reload every time. INFERRED, unverified.
- `--no-context-shift` must stay (contract test in launch.rs:234). The history rules (every tool call keeps its result, pins and summary in the system message) depend on the server never silently dropping tokens. 'Auto compresses' must stay app-side.
- Reloading kills the running server. A reply in progress ends with an error, and llama-server's cached prompt is lost, so the first reply after a reload re-reads the whole conversation (slow on CPU). Inserting or changing a summary changes the system message and also invalidates the cache (ARCHITECTURE 8.5 'Stable prefix'). Proactive compression should run when that cost is acceptable.
- Memory: the KV cache grows linearly with context (kv_bytes_per_token, fit.rs:73-76). A larger per-model context can fail to load (out of memory, then step-down to a slower backend) or load but run slowly on NVIDIA (spill into system RAM, reported as 'loaded but slow'). Keep the trained-length cap (models_cmd.rs:58-67) and the 512..=1,048,576 range. ARCHITECTURE 1.4 expects about 16k for an 8B model on the owner's 16 GB Mac.
- Security: summary text is model output. It is sanitised (sanitizer.clean) inside the reserved <conversation_summary> tag, and must be shown in the UI as plain text, never markup (same rule as the Context inspector, 13.13). A user-editable or user-written summary would need the same sanitiser and reserved-tag escaping. Pins must never be compressed (PINNED_FIT_PERCENT rule; a turn with oversized pins refuses instead).
- The Context inspector must be built by the same code as a real turn (turns::assemble Preview plus agent::preview_turn). Any new stage or proactive compression must show up in NextCompaction / next_drop and keep the test the_preview_is_the_first_request_of_the_turn passing.
- Storage: a new key in the settings key/value table (JSON value) needs no migration. A new table or column needs MIGRATIONS V3 (schema.rs:414). Per-model keys should not use the absolute path alone, or moving a file would lose its setting (profile.rs uses file name + size + backend).
- Only one turn runs at a time and only one local model is loaded. A per-chat context (instead of per model) would force a reload whenever the user switches chats.

### Suggested approach

1) Per-model context. Add a server-side lookup, `settings::context_for_model(path)`, that reads a per-model record (a settings key such as `modelLoad:<16 hex of SHA-256(file name + size)>` holding `{ctx}`; a later item 2 could add more load options to the same record) and falls back to the global `localModel.ctx`. Make load_local_model resolve the context itself (so ModelsDialog, the model picker and FirstRun no longer pass it), keep the trained-length cap, and offer an 'Automatic' choice that uses models::fit::check's suggested_ctx so the context fits the computer's memory. Add commands get/set_model_load_settings(path). In the UI, add a per-model choice in plain words in the Models dialog, the model picker and the first-run screen (for example 'Short memory: about 6 pages', 'Medium', 'Long', 'As much as this computer can handle'), show the model's maximum, and add 'Apply (reloads the model)'. The reload should wait for a running reply and then show the existing load progress. For endpoints, optionally add a per-endpoint-model override that wins over the reported size, falling back to remoteContextLength. 2) Auto compression is already automatic; make it visible and robust. Have the 'compacted' event carry what happened, and replace the three notes with plain words: 'Older tool results were shortened to save room.' / 'The start of this conversation was summarised so it still fits.' / 'The server said it was too long; making room and trying again.' Add `summary: {coversUpTo, text}` to ChatDetailDto (from latest_summary_on_path) and draw a lasting divider in the chat ('Earlier messages are summarised for the model — Show summary', plain text). Say so when summarising fails. Optionally run stage 1/2 proactively after a turn ends, or right after a reload to a smaller context, when the chat is over, say, 70% of the new budget, so the next reply does not wait. Optionally add a 'Make room now' button in the Context tab. 3) Make a context change safe. When the summary plus loaded skills are what push F over its share, fold the summary again (allow summarise() to re-summarise the summary alone under the new cap) or drop loaded skills with a note, instead of the misleading tools refusal. Count the summary in tool_select::other_fixed. Cut attachment text to a share of the context when building the prompt, the way mentions are (resolve::cap_chars). Re-check the header meter against the turn's n_ctx. 4) Tests in crates/agent/tests/turn_loop.rs: 'a chat summarised at 32k continues at 4k', 'an oversized old summary is folded, not refused', 'an attachment larger than the context is shortened'. Update the context_cmd preview tests and add an e2e for the per-model setting surviving a reload. Update ARCHITECTURE 7.3/8.4/8.6 (the missing divider and attachment truncation).

### Open questions

- Should the context size belong to the model (a natural fit, since one model is loaded at a time and chats bind to `local:<path>`) or to the chat? A per-chat size would force a reload when switching chats.
- Should the default per model be 'Automatic: as much as fits in memory' (using the fit check) instead of the fixed 8,192, and should it include the backend (memory differs by backend; the evals profile key does)?
- Should 'auto compresses' also give the owner an on/off switch or a 'how early' choice? Turning it off would make long chats fail with 'context_full' instead.
- Should the owner be able to read the summary in the chat, edit it, or throw it away? Editing adds sanitising and reserved-tag rules.
- When the owner changes a loaded model's context, reload immediately (ending any reply in progress) or at the next message?
- Should endpoints (Ollama, LM Studio, vLLM) get a per-model size override too, or only local models?
- Should the app compress ahead of time (after a reply ends, or right after a reload to a smaller size) so the owner never waits for a summary at the start of a reply, accepting that llama-server re-reads the conversation at that moment?
- The documented 'Earlier messages were summarised' divider (ARCHITECTURE 8.4) and the token-budget cut for long documents (8.6) are missing from the code: fix them in 0.0.5 or correct the document?

## Model catalog and Hugging Face browse/download (0.0.5 item 4: compare models and what they are good at)

The app knows about models from four places. (1) A signed, curated catalog bundled at build time (catalog/models.json, compiled into the app with include_str!). It has 14 entries in 5 memory tiers with pinned commit, files, sizes, SHA-256, quant, a capabilities list (tools/vision/thinking), license and gated. Every "tested", "memoryAtRecommendedCtx", "sampling" and "minLlamaBuild" field is empty, and there is no description or strengths field. (2) Hugging Face API answers: search gives downloads, likes, gated, license, lastModified and pipeline_tag. Detail gives the commit, files with size and SHA-256, the gguf block (architecture, context length, parameter count, chat template), and tags/cardData, but only the license is taken from tags/cardData; the rest is thrown away. The model card README is shown as plain text. (3) The GGUF header, read from a 6 MiB ranged fetch before download or from the file after it, gives ModelSummary: architecture, context length, quant, MoE, layers/heads, and tools/thinking template guesses. (4) A memory fit check against this computer, giving a green/yellow/red verdict and one sentence. The catalog appears only on the first-run screen and as a version number plus a Refresh button in Settings. After first run, Models → Browse is pure Hugging Face search. Catalog Refresh exists and is signature-checked, but it is disabled in every build so far because the committed updater public key is empty. Older app versions ignore extra catalog fields: I confirmed this by running the current parser against a modified copy. A schemaVersion bump makes every existing parser reject the catalog. Nothing today compares models. The 0.0.4 evals give per-model data on this computer: model check profiles under settings keys `modelProfile:<16 hex>`, and benchmark runs saved as JSON files that can already be compared two at a time. Neither is linked to a catalog entry or a Hugging Face repo.

### Gaps for the request

- No curated 'what it is good at' data anywhere. The catalog Entry has no plain-language summary, strengths/uses, parameter count, active parameters for MoE, publisher/family, languages or release date, and there is no fixed vocabulary for strengths. Adding any of it needs new optional fields in Entry (catalog.rs:63-91) plus catalog content written and checked by a person.
- Catalog entries are visible only on the first-run screen. Models → Browse is pure Hugging Face search and the Installed tab has no catalog view, so there is nowhere to browse, pick or compare catalog models after first run. A new command is needed that returns catalog entries with fit, installed state and local results (first_run_info returns SuggestionDto, but only for first run).
- No compare UI or selection model: users cannot tick two or more models (catalog entries, HF repos or installed models) and see them side by side. The only existing side-by-side is CompareTable for two benchmark runs.
- Hugging Face facts that would help are fetched and then dropped. tags (in search and detail) and cardData (base_model, language, pipeline_tag, license_name/link) are parsed only for the license (hf.rs:304-309, 749-754). RepoSummary.likes, lastModified and pipelineTag reach the UI but are not shown. Showing them needs new fields in RepoDetail/RepoView/RepoSummary rendering.
- Hugging Face facts are not saved at download time, so they disappear offline. StoredSummary (hub.rs:591-610) keeps only GGUF-derived badges. Keeping comparison working offline means saving, say, pipeline_tag, base model, languages, parameter count, license and the catalog id into gguf_summary (or a new column) when the download finishes. register_model ignores GroupMeta.catalog_id.
- No link between eval results and models. Profiles are keyed by a hash of file name + size + backend, and benchmark runs carry the label 'file (backend)'. Neither carries repo, catalog id or sha256. Showing 'your results on this computer' next to a model means matching by file name + size against the models table (or adding the repo/catalog id to new runs), plus a new command that lists all profiles (new Store method to list settings by the `modelProfile:` prefix).
- Installed models have no fit verdict, and catalog fit uses only file sizes + 1.5 GB (no KV estimate at a chosen context). For a fair memory/speed comparison, one fit function at the same context would have to cover catalog entries, HF variants and installed files. The catalog has no header data before download unless fields like kvBytesPerToken or context length are added.
- Plain-language strings are missing. Today the UI shows jargon ('Q4_K_M', 'MoE', 'tools', 'thinking', raw architecture names like the GGUF general.architecture value, 'gated', capability words joined raw). A compare view needs one mapping from these keys to plain words, e.g. 'Can use tools', 'Can see images', 'Thinks before answering', 'Smaller file, a little less accurate'.

### Risks and constraints

- Signed catalog. The minisign signature covers the exact bytes of models.json (verify_refresh, catalog.rs:256-276), and release.yml signs catalog/models.json at release time (lines 174-183) and checks that the uploaded copy is byte-identical (261-265). Any edit needs re-signing, which the release job does automatically when TAURI_SIGNING_PRIVATE_KEY exists. Today the committed pubkey is empty, so no build can Refresh. New fields reach users only in a new app build.
- Keep schemaVersion at 1 and make every new field optional (#[serde(default)], Option or Vec). I ran the current parser: unknown fields are ignored, but schemaVersion 2 is rejected by every existing parser ('unsupported schema version 2'). A required new field would also break the signed test fixture crates/models/tests/fixtures/catalog/models.json. Its secret key was discarded (fixture README), so it cannot be re-signed, only replaced with a new throwaway key pair.
- Bump `sequence` whenever catalog content changes. current_catalog prefers a stored refreshed catalog only when its sequence is higher than the bundled one (hub.rs:891), and Refresh accepts only higher sequences.
- Rule 'No model name appears in code' (catalog.rs:4, ARCHITECTURE 11): comparison text and 'good at' claims must come from catalog JSON, not hardcoded TypeScript or Rust.
- Offline rule: the app must work offline once a model is downloaded. The bundled catalog, hardware detection, installed models and eval results are local. Hugging Face facts and the model card need the network, and opening Browse fires a search immediately (ModelsDialog.tsx:353-358). An offline comparison must rely on the bundled catalog plus facts saved at download time. Online-only columns should say so rather than show errors.
- No invented benchmarks. Hugging Face can expose `evalResults` and `model-index` (docs/research/huggingface.md:28). These are self-reported by uploaders, usually missing on GGUF re-uploads (unsloth, ggml-org), and untrusted. If shown at all they must be labelled 'reported by the publisher', and they are better left out. The 0.0.4 evals are tiny (3 probes, 11 tasks), run on the user's own hardware, and noisy: ARCHITECTURE 13.14 says a 0.6B model chose different settings in two runs. They must be labelled as the user's own results on this computer, not as model quality.
- Licence honesty: Hugging Face license tags are self-declared. The research doc says Gemma 4 is tagged apache-2.0 but links to a separate Gemma 4 licence (huggingface.md:212), and the catalog lists all three Gemma entries as spdx apache-2.0. A comparison column for licence could mislead without the catalog's license name/url.
- Untrusted remote content: tags, cardData and the README card are uploader-controlled strings. Show them as plain text only, as the card is shown today (in a <pre>), never as HTML or markdown links. Never pass them into prompts or let them override signed catalog facts.
- Network policy: every Hugging Face request must keep going through HfClient (token only to huggingface.co, no automatic redirects, CDN host allow-list). Extra expand[] fields in the existing detail call cost nothing. New per-repo calls (for example fetching the base model's card to compare) add requests and anonymous rate-limit pressure (429 is handled as RateLimited). Bulk-fetching details for many repos to fill a comparison table would hit the rate limit.
- The ARCHITECTURE claim of a lint enforcing one HTTP module is not true today (clippy.toml covers only process spawning). Reviewers should not rely on it when new fetches are added.
- Settings keys: catalog data lives in settings `catalog` (not writable from the webview) and profiles in `modelProfile:*` (refused by set_setting's allow-list, models_cmd.rs:193-198). Any new comparison preferences must use their own commands or a narrow allow-list entry, not widen set_setting.
- Matching identities is fuzzy. Profiles hash file name + size + backend, so the same file on Vulkan and on CPU gives two profiles, and a renamed or imported copy gives another. A catalog match by repo + first file path + sha256 works only for downloaded models (imports have repo NULL and sha256 NULL, hub.rs:767).

### Suggested approach

Build the comparison only from facts the app can stand behind, each labelled with where it came from. (1) Catalog: add optional, signed, curated fields to Entry with schemaVersion still 1, every field #[serde(default)], and sequence bumped to 2. Suggested fields: a plain one-sentence `summary`; `goodAt` taken from a small fixed vocabulary (for example everyday chat, writing, coding, reading images, long documents, many languages, speed on modest hardware) that the app maps to plain words and that ignores unknown keys; `parameters` and, for MoE, `activeParameters`; `publisher`; `languages`; `released`; and optionally `contextLength`. The owner or a maintainer writes and reviews these and the app never generates them. Older apps ignore them (verified). Map the existing capabilities (tools/vision/thinking) to plain phrases as well. (2) Hugging Face: in parse_repo_detail, also keep pipeline_tag, the base model (cardData.base_model or the `base_model:` tags), languages and license_name/link from the data already downloaded. Show them as plain text marked 'from Hugging Face (set by the uploader)'. Show likes and last updated in search results. Do not show publisher eval numbers. (3) This computer: compute one fit verdict for every column at the same context with the existing fit::check. For catalog entries without a header, use the current file-size estimate and say it is approximate. (4) Your results: add a read-only command that lists all `modelProfile:*` profiles (new Store prefix query) and the BenchSummary list, and match them to installed models by file name + size (and to catalog entries via the models row's repo + sha256). Show them as 'On this computer: passed 2 of 3 checks, 7 of 11 coding tasks' with the date, plus a link to the existing CompareTable. (5) Offline: when a download finishes, save the catalog id and the Hugging Face facts into gguf_summary JSON (StoredSummary fields are all #[serde(default)], so no migration), so comparing installed and catalog models works without a network. (6) UI: a 'Compare' action that lets users tick models from a new catalog list (shown in the Models dialog, not only at first run), the Installed tab and Browse results. Show a simple table in plain language, with rows like 'Good at', 'Can see images', 'Can use tools', 'Thinks before answering', 'Download size', 'Fits this computer', 'Your test results' and 'Licence', each with its source noted. Keep no model names in code.

### Open questions

- Who writes and signs off the curated 'good at' text for the 14 catalog entries, and from what sources (publisher announcements, the owner's own use)? It must not be invented, and the app cannot verify it.
- Should the owner create the updater key pair for 0.0.5, so Refresh can ship catalog improvements between releases? Without it, catalog changes only arrive with app updates, and Refresh stays disabled with the current message.
- Should comparison cover only catalog and installed models (fully offline), or also arbitrary Hugging Face search results (online-only, uploader-supplied facts, rate-limited)?
- Should publisher-reported eval numbers (Hugging Face evalResults/model-index) ever be shown, clearly marked 'reported by the publisher', or left out completely? The honest default is to leave them out.
- Are the Gemma entries' licence fields (spdx apache-2.0) correct, or should they carry the Gemma licence name/url before a licence column is shown side by side?
- Should 0.0.5 also implement the documented-but-unused catalog fields (sampling overrides, minLlamaBuild), and the second-tier llama-fit-params check, which is discovered but never run? That would make 'fits this computer' more accurate for the comparison.
- Should benchmark runs and profiles start recording repo, sha256 or catalog id from 0.0.5 on, so later comparisons can match results to models reliably? Older runs would still need matching by file name + size.

## Item 3: letting locally loaded models "talk to Claude or Codex apps upon user request". Covers both directions: (A) Claude Desktop, Claude Code or Codex use this app's local model; (B) the local model, inside this app, hands work to Claude Code or Codex installed on the computer.

Neither direction is built today. There is no setting, tool, endpoint or MCP server for it, and no earlier mention in ARCHITECTURE.md, SPEC, MILESTONES or CHANGELOG.

The raw parts for direction A already exist. The pinned llama-server (b12110) listens on 127.0.0.1 and already speaks all three APIs these apps need: the Anthropic Messages API (/v1/messages and /v1/messages/count_tokens), the OpenAI Responses API (/v1/responses) and Chat Completions. I confirmed this by running the binary. I also ran Claude Code 2.1.322 headless against it and got a correct answer. Three things stop other apps from using it today, all on purpose:
- it gets a new random port and a new random key on every launch, and the key is never shown;
- it runs only while the app has a model loaded;
- it has a single slot and an 8,192-token context by default. Claude Code's first request alone was 11,088 tokens.

Direction B already "works" with no code changes. With the Terminal tool on and a folder approved, the local model can call run_command with `claude -p "..."` or `codex exec "..."`. But the policy gate treats these as ordinary commands. A probe of the real classifier showed `claude -p "..." --dangerously-skip-permissions` is not flagged as a network program and is not kept-asking. So under Allow all it runs with no card, even after untrusted content entered the turn. Commands also have a 600-second ceiling and lose secret-looking environment variables.

The MCP route for B is weak:
- `claude mcp serve` exposes Claude Code's tools (Bash, Read, Edit), not the Claude model;
- `codex mcp-server` has been removed from Codex (official docs).

The MCP host already in the app refuses sampling and declines elicitation.

### Gaps for the request

- Direction A (other apps use the local model): there is no user-facing 'Share the loaded model with other apps' switch. It would need:
- a stable address: a fixed port the user can see, or a stable proxy port;
- a separate sharing key, kept in the keychain, that can be copied and replaced (llama-server already accepts a comma-separated LLAMA_API_KEY list, so the app keeps its own private key);
- a status line such as 'Other apps can use: <model> at http://127.0.0.1:PORT';
- clear behaviour when no model is loaded or a model is reloading.
- Direction A: no per-app setup help. It needs copy-ready snippets with the real port, key, model name and context size:
- Claude Code: the env block for ~/.claude/settings.json, or shell exports of ANTHROPIC_BASE_URL, ANTHROPIC_AUTH_TOKEN, ANTHROPIC_MODEL, CLAUDE_CODE_MAX_CONTEXT_TOKENS and CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC.
- Codex: a config.toml provider block (base_url http://127.0.0.1:PORT/v1, env_key, wire_api="responses", model_context_window).
- Claude Desktop: Developer Mode steps and the Gateway base URL and key fields.
- Direction A: the context size is one global 8,192-token setting. Sharing needs per-model context (overlaps item 1) and a clear warning when the context is under about 32k, because Claude Code alone sends about 11k tokens.
- Direction A: one slot (-np 1). An outside app and the in-app chat queue behind each other and push each other's prompt cache out. There is no queueing, notice or 'pause sharing while I chat' rule.
- Direction A: no audit trail or visibility of outside use. llama-server logs are not mapped to audit rows. An app-owned proxy would be needed to record 'Claude Code used the local model at 14:02, 11,088 tokens in'.
- Direction A, if 'talk to' means Claude or Codex calling the local model as a helper tool: the app has no MCP server mode. It would need a hidden-flag stdio worker (main.rs pattern) exposing for example `ask_local_model {prompt}`. It also needs a safe way for that worker to reach the running app or llama-server; no local IPC exists today, and writing the port and key to a file would put a secret on disk. Codex's default 60 s MCP tool timeout is shorter than many local generations.
- Direction B (local model hands work to Claude Code or Codex): there is no dedicated tool and no detection of whether `claude` or `codex` is installed and logged in. The model is not told they exist, so it would need a skill, a pinned instruction or a tool description.
- Direction B: the policy has no idea what claude and codex are. They are not network programs, `--dangerously-skip-permissions`, `--permission-mode bypassPermissions` and `--dangerously-bypass-approvals-and-sandbox` are not recognised, and Allow all lets them run with no card. A dedicated describer or Scope (for example Scope::ExternalAgent{agent, folder}) with keep_asking and network=true is missing.
- Direction B: the 600 s terminal ceiling and the 1 MiB output cap are too small for long agent runs. There is no streaming of Claude Code stream-json or Codex --json progress into the tool card, and no 'final answer only' extraction.
- Direction B: the app's git tool turns off repository hooks (ARCHITECTURE l.655), but a `claude -p` it starts would run repository-controlled hooks and .mcp.json servers unless --bare is used. --bare needs an API key, which looks_secret strips.
- Direction B: no plain-language warning that the task text and any files Claude or Codex read leave the computer for Anthropic or OpenAI, using the user's subscription or billing. The 13.6 network table has no row for this, because a child process's traffic is 'outside that module'.

### Risks and constraints

- Security model promise (ARCHITECTURE l.814): llama-server is 'Loopback only, random port, per-launch key'. Sharing breaks 'random port' and 'per-launch key', so 13.1, 7.3 and SECURITY.md must be rewritten. Loopback-only must stay: never offer 0.0.0.0, LAN access, or llama-server's --connect tunnel. Note the environment is scrubbed of LLAMA_ARG_* (7.3) precisely because LLAMA_ARG_CONNECT and LLAMA_ARG_TOOLS exist.
- Any program on the computer that learns the sharing key can use the model: other user accounts on a shared Mac or PC, malware, a browser extension with native messaging. CORS 'none' still blocks web pages (verified), and /health stays readable without a key (verified), which reveals that something is listening. The key must live in the keychain, be shown only on request, be replaceable in one click, and be off by default. Writing it into ~/.claude/settings.json or a shell profile puts it in plain text; Claude Code's own docs warn against committing it in a project's .claude/settings.json.
- A fixed port can be taken by another program first. The existing check (server.rs l.328-366: wrong key or different model means PortOwnedByOther) protects the app, but the outside app could then be talking to an impostor on 'our' port. A proxy owned by the app on a stable port, with llama-server staying on a random port behind it, avoids handing out a port the app does not control.
- Starting llama-server with extra flags such as --tools, --mcp-servers-config or --agent must never be part of this feature. The help text says 'do not enable in untrusted environments'; they would give any key holder a shell and file access.
- Anthropic's docs state they do not support routing Claude Code to non-Claude models through a gateway. It works today (verified with 2.1.322), but any Claude Code update can break it. Present it as 'experimental, may stop working after a Claude Code update', not as a promise.
- Local models are slow and small for these apps. Claude Code's minimal request was 11k tokens and took about 3 minutes on CPU with a 0.6B model. Its tool set expects a strong model, so small models will often fail tool calls. Codex sends its own tool set (shell, apply_patch) over the Responses API; llama-server's Responses compatibility with real Codex traffic is unverified, since Codex is not installed here.
- Contention: with -np 1, an outside app's 11k-token request pushes the in-app chat's prompt cache out and makes the next in-app turn slow; requests wait for each other. Raising -np splits the context between slots and uses more memory on 16 GB machines (7.3 chose -np 1 on purpose).
- Reported model id = full GGUF path (verified). It reveals folder names, often including the user's name, to the outside app and any logs it keeps. Use --alias or a proxy to give a short public name.
- Direction B, the local model starting Claude Code or Codex is a capability jump:
- Those programs run as the user and can edit anything, including the app's own database, approved-folder list and audit log. ARCHITECTURE l.919 already states the app's guarantees do not hold against other processes.
- `claude -p` without --bare runs repository hooks and .mcp.json servers even in untrusted folders (Claude docs); the app's git tool forbids that kind of repo code for good reason (l.655).
- An untrusted web page or file the local model read can prompt-inject a task into Claude or Codex. Today that runs with no card under Allow all (verified classifier result). D9 does not catch it because claude and codex are not network programs.
- Direction B data leaving the computer: the task text plus whatever files Claude or Codex read go to Anthropic or OpenAI and are billed to the user's account. This contradicts the app's local-first pitch unless the user asks for it each time. It needs an always-ask card, or at least one per chat, that says so in plain words.
- Direction B platform differences: Windows commands go through Windows PowerShell 5.1 (no && or ||). Whether Claude Code on Windows needs Git Bash is unverified. On macOS, zsh -lc with the captured login environment should find claude and codex installed with npm, Homebrew or native installers. The terminal drops secret-looking variables, so only logins stored in the tools' own files or keychain work.
- MCP route for B: adding `claude mcp serve` as an external server gives the local model Claude Code's Bash, Read and Edit tools with only the generic external-tool card (exact arguments). It bypasses the path sandbox and the terminal classifier, which is a weaker shell than the app's own terminal, and it is not 'talking to Claude'. `codex mcp-server` no longer exists. The app declines elicitation, which Codex's old MCP mode used for approvals.
- Release discipline: section 7.1 says every llama.cpp bump must pass contract tests. If the app relies on /v1/messages and /v1/responses for sharing, add contract tests for those endpoints (and for multi-key LLAMA_API_KEY), since 'Flags, defaults, log lines and HTTP fields can change in any release'.
- Settings that change permissions must stay under the 13.5 rule: only main-window UI commands may change them, never a tool or the model. The sharing switch and key must be changed only by user commands, never by a tool, a skill or an MCP server.

### Suggested approach

Treat item 3 as two separate, opt-in features. Ship Direction A first, because almost everything it needs already exists and was verified. Keep Direction B narrow and always-asking.

Direction A, plain name "Let other apps use this model" (Settings → Local models, or a new "Other apps" tab):
1. Off by default. Turning it on shows a one-time warning in plain words: "Programs on this computer that have the key can send prompts to your loaded model. Nothing leaves the computer."
2. Generate a sharing key into the keychain. Pass it to llama-server as a second key (LLAMA_API_KEY="<appKey>,<shareKey>", verified to work), so the app's own key stays private. A "Replace key" button restarts the server.
3. Give other apps a stable address. Simplest: a user-visible fixed loopback port with a conflict message. Better: a small proxy owned by the app on a stable 127.0.0.1 port in front of llama-server. hyper 1.12 is already in Cargo.lock but is not a direct dependency. A proxy can:
   - answer "No model is loaded in harnessUI" while the model is unloaded or reloading;
   - rename the model id from the file path to a short name;
   - write one audit row per outside request ("Claude Code used the local model");
   - queue outside requests behind the in-app chat;
   - allow only /v1/messages, /v1/messages/count_tokens, /v1/responses, /v1/chat/completions and /v1/models.
   Never bind beyond loopback.
4. Show copy-ready setup cards with real values:
   - Claude Code: an env block for ~/.claude/settings.json with ANTHROPIC_BASE_URL, ANTHROPIC_AUTH_TOKEN, ANTHROPIC_MODEL=<short name>, CLAUDE_CODE_MAX_CONTEXT_TOKENS=<loaded ctx> and CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1.
   - Codex: a config.toml block, model_provider = "harnessui" plus [model_providers.harnessui] base_url = "http://127.0.0.1:PORT/v1", env_key, wire_api = "responses", model_context_window.
   - Claude Desktop: the Developer Mode → Configure Third-Party Inference steps, with Gateway base URL and key.
   Each card says "Experimental: Anthropic and OpenAI do not officially support local models here; an update to those apps may break it."
5. Warn when the loaded context is under about 32k ("Claude Code needs at least 32,000 tokens of context; this model is loaded with 8,192"). Link to the per-model context setting from item 1.
6. Update ARCHITECTURE 7.3, 13.1 and 13.6 and SECURITY.md. Add contract tests for /v1/messages, /v1/responses and multi-key auth on the pinned build.

Optional A-variant (Claude or Codex call the local model as a helper): a hidden-flag stdio MCP worker in the app binary (main.rs pattern, rmcp already compiled with server support) with one tool, ask_local_model. It talks to the running app through the proxy above, using the sharing key from the keychain rather than a file, so the user pastes {"mcpServers":{"harnessui":{"command":"<app path>","args":["--mcp-serve"]}}} into Claude Desktop or Claude Code, or a [mcp_servers.harnessui] block into Codex with tool_timeout_sec raised.

Direction B, plain name "Ask Claude Code / Codex for help": a new built-in tool group, off in every chat and switched on per chat like Subagents. It offers ask_claude_code {task} and ask_codex {task}, shown only when the program is found on PATH, with a "not installed" note and link otherwise.
- The tool runs fixed argument templates, never model-chosen flags:
  - Claude: `claude -p <task> --output-format stream-json --permission-mode <user choice: plan | acceptEdits>`, never bypass, ideally with --bare when the user has an API key configured.
  - Codex: `codex exec --json --sandbox <read-only | workspace-write> <task>`.
- The working folder must be an approved folder (path sandbox).
- Longer timeout (for example 30 minutes) with Stop killing the process tree. Progress streams into the card; only the final answer returns to the model, as untrusted tool output.
- Policy: a new Scope with keep_asking=true and network=true. Every call shows a card even in Allow all: "This sends your request and files Claude Code reads to Anthropic, using your Claude account."
- Separately, add claude and codex to the classifier's network list, and treat their bypass flags as keep-asking, so the raw run_command route cannot skip the card.
- Do not recommend adding `claude mcp serve` as an MCP server for this purpose.

### Open questions

- Which direction does the owner mean by 'talk to Claude or Codex apps'? (A) Claude Desktop, Claude Code or Codex use the app's local model; (B) the app's local model asks Claude Code or Codex for help; or (C), a third reading: use Claude or OpenAI cloud models inside this app. C is partly covered: Endpoints accepts any OpenAI-compatible URL with a key, but there is no Anthropic Messages client.
- For A, is a fixed, user-visible port acceptable, or should the app own a small proxy? A proxy is more code, but gives a stable address, audit rows, friendly 'no model loaded' errors and protection of the in-app chat.
- For A, should outside requests be allowed while the user is chatting in the app (shared single slot, slower), queued, or refused with 'busy'?
- For A, does the owner accept the 'experimental' framing? Anthropic's docs say routing Claude Code to non-Claude models is unsupported, even though it works with Claude Code 2.1.322 and the pinned llama-server.
- For A, Claude Desktop: does Configure Third-Party Inference accept an http://127.0.0.1 base URL? The docs show only https examples. This is unverified and needs a test on a real Mac or PC.
- For A, Codex: does real Codex traffic (its shell and apply_patch tools, reasoning and store fields) work against llama-server's /v1/responses? Codex is not installed here, so only curl-level Responses calls were verified.
- For B, should each call to Claude Code or Codex always ask (recommended, because it sends data and spends the user's subscription), or may 'Allow for this chat' cover it?
- For B, should the app pass the user's ANTHROPIC_API_KEY or OPENAI_API_KEY through to these programs? Today looks_secret strips them, and --bare mode for Claude Code needs one. Or should it rely only on the CLIs' own stored logins?
- For both directions: should the raw run_command path also be tightened now (claude and codex treated as network programs, bypass flags kept-asking), even if no dedicated tool ships in 0.0.5?

## User interface and wording around models and model settings (Settings > Local models, Models dialog, model picker and load flow, Tested settings/benchmarks tables, IPC, style tokens)

Today every model load setting is global, and the screens only offer two of them: Backend and Context size, under Settings > Local models (SettingsDialog.tsx:369-489). They are saved straight away to the `localModel` setting and take effect "the next time a model loads". You load a model in one of four places: Models > Installed > "Use", the chat header's model picker, the Welcome card, or first run. All four read the same global settings (getLocalModelSettings) and call load_local_model. There is no Reload button and no Unload button: to reload with new settings you pick the same model again. The backend then restarts it only if the context size or backend changed (models_cmd.rs:70-80). The app already summarises older messages on its own when a chat gets full (agent loop, ARCHITECTURE 8.4). The interface only shows this as a short-lived note. Some things are fixed in code with no control: the device (it exists in the settings data but nothing on screen sets it), GPU layers (all or none), the prompt cache (512 MiB) and the thinking budget. There are two per-model precedents: Tested settings (`modelProfile:<hash>`) and the computer-use convention (`computerProfile:<model ref>`, with a Model dropdown). There is also one comparison precedent: the benchmark CompareTable puts two runs side by side. The Models dialog has no comparison view. The catalog only lists capabilities (tools/vision/thinking), with no plain-language "good at" text. Wording is mostly plain, but GPU and runtime terms leak through: raw backend ids like "vulkan", "Vulkan0", GGUF, quantization labels like Q4_K_M, MoE, projector, tokens, llama.cpp, and llama.cpp's own stage names.

### Risks and constraints

- Text rules (docs/dev/0.0.4/spec.md:86-88): plain, short, no jargon, no exclamation marks, and never put names or identifiers of AI models or assistants into code, comments, tests or docs. ARCHITECTURE 11 also says 'No model name appears in code'. Model strengths for a comparison must come from data (the signed catalog), not hard-coded strings. Request #3's UI wording naming specific assistant apps conflicts with this rule and needs a decision.
- e2e scripts click exact labels: 'Use' (e2e/m2_models.py:128), 'Local models', 'Tested settings', 'Check this model' (e2e/m9_model_check.py:118-123; e2e/scripted_agent.py:2540-2542, 2597), the full settings tab list 'General','Local models','Endpoints','Hugging Face','MCP servers','Skills','Git','Browser','Computer use','Permissions','Audit log','Diagnostics' (scripted_agent.py:299-300), and 'Local models' in e2e/m8_offline.py:35. e2e scripts also call load_local_model with {ctx, backend, device} (m1_chat.py:136, m3_agent.py:91, etc.). Renaming labels or changing the settings shape breaks these.
- Unit tests pin wording: Welcome.test.tsx ('Pick up where you left off', /Open a GGUF file/, 'Ready on vulkan · Vulkan0 · 65,536 context', 'Chat with it'), FirstRun.test.tsx (hardware sentences, 'Download', 'none is preselected automatically'), and evals.test.tsx (the exact check and benchmark dialog texts, and FORBIDDEN_LABELS ['Allow once','Deny','Save','Use','Continue','Send','Stop'] for run-confirm start buttons). Changing backend display names changes the Welcome test.
- The generic set_setting command only accepts theme, defaultSystemPrompt, remoteContextLength and stepsPerTurn (models_cmd.rs:186-194). modelProfile keys are deliberately unwritable through it. New per-model load settings need their own validated command (ctx 512..1,048,576 as in set_local_model_settings 108-112).
- Model identity: modelProfile hashes file name + size + backend, so a per-backend profile breaks when the backend changes. computerProfile keys by model ref, which includes the full path and breaks if the file moves. Choose one deliberately for per-model load settings. A per-backend key would make a context setting vanish when the backend switches.
- Reload semantics: load_local_model is a no-op only when ctx and backend match (models_cmd.rs:70-80). New settings such as GPU layers or the thinking budget must be added to that comparison and to LoadTicket same_in_progress (runtime_manager.rs:532-539), or 'Reload' will silently do nothing.
- Request #3 changes a trust boundary. llama-server is deliberately loopback-only with a per-launch key in an environment variable, CORS closed and --no-slots (ARCHITECTURE 7.3, 13.x). Exposing a model to other apps needs its own design: key storage in the keychain, never in plain files (docs/SPEC.md:31), loopback only, an audit entry, and a confirmation. Requests from another app would bypass the app's tools/approval pipeline unless they are routed through it.
- Model cards and hub data are untrusted remote content, shown as plain text with images blocked (ARCHITECTURE 11). A comparison view must not render card HTML or treat card text as instructions. Each hub_repo call spends the anonymous HF rate limit, which is why Browse debounces at 400 ms.
- Layout limits: the Settings dialog is a fixed h-[34rem] w-[48rem] with a w-44 tab rail (SettingsDialog.tsx:896, 905). The Models dialog is h-[38rem] w-[52rem] (ModelsDialog.tsx:568). Both cap at max-w-[94vw]. A comparison table of 3-4 models needs overflow-x-auto, as the existing tables do, or rows as attributes.
- Units are inconsistent: the device list uses totalMib/1024 'GB' (binary), while formatBytes is decimal GB 'as Hugging Face shows'. A plain-language memory figure in a new panel should pick one.
- Every Tauri command checks the calling window for eval commands. New commands for exposure, reload or per-model settings should follow the same main-window-only pattern (evals/commands.rs:60).

### Suggested approach

Keep the existing structure and add to it.

(a) Per-model panel. Add a 'Settings' button (gear icon, aria-label 'Settings for <file>') next to 'Use' on each Models > Installed row (ModelsDialog.tsx:158). It opens a sub-view with a 'Back to installed' link, copying RepoDetail's 'Back to results' pattern (218-220).
- The sub-view lists the model's facts in words, then 'How much of the conversation it can remember' (context size). Options: 'Same as the default (8,192)' and fixed sizes, each with a rough word count ('about 6,000 words'). Add a live FitBadge for that size and a note when the model was trained for less ('This model was made for up to 32,768; larger sizes are reduced to that.').
- Fold the automatic summarising into the same panel as a plain sentence: 'When a chat gets close to full, the app summarises older messages so it can keep going.' Add a lasting divider in the chat when it happens.
- A 'More options' disclosure holds graphics-card share (GPU layers: 'All on the graphics card (fastest)' / 'Part on the graphics card' / 'Processor only (slowest)'), device ('Which graphics card'), and thinking budget ('How long it may think before answering').
- Footer buttons: 'Load with these settings', or 'Reload now' when it is the loaded model.

(b) Settings > Local models stays as 'Defaults for all models'. Keep the 'Local models' tab name and the 'Use' / 'Check this model' labels for e2e, or update the e2e scripts in the same change. Relabel backends with a display map: 'Graphics card (Vulkan)', 'NVIDIA graphics card (CUDA)', 'AMD graphics card (ROCm)', 'Apple graphics (Metal)', 'Processor only (slower)'. Add per-select help with aria-describedby, as RemoteContext does (682-689).

(c) Reload. Add a Radix Popover on RuntimeIndicator, styled like ToolsPanel (ToolsPanel.tsx:196-210). It shows 'Loaded with …', 'Reload', 'Change settings…' (opens the panel from (a)) and 'Unload to free memory' (ipc.unloadModel). Show a 'Settings changed – reload to apply' warning chip when the stored settings differ from what is loaded.

(d) Comparison. Add a fourth tab 'Compare' to the Models dialog (Tabs.List 577-581). Add 'Add to comparison' to Browse result rows, RepoDetail and Installed rows, with up to 3-4 models. Rows are plain questions: 'Fits this computer?', 'Download size', 'Can use tools', 'Can read images', 'Can think step by step', 'Longest conversation it was made for', 'License', 'Downloads', 'Good at' (from new catalog fields such as goodAt/bestFor; 'No description yet' for other repos), 'Your test results' (Tested settings and benchmark totals when present). Use the Benchmarks table style (text-xs, border-t rows, overflow-x-auto) plus a caption.

(e) Request #3. Add an opt-in section behind an AlertDialog confirmation, in the style of checkConfirm's plain bullet lines: on/off, address and key with 'Copy', what the other app can and cannot do, and stop sharing. Wording must not name specific assistant apps in code (see open questions).

Copy these plain-language patterns:
- StepsPerTurn help
- RemoteContext help
- FitBadge sentences
- The thinking toggle titles
- The checkConfirm lines
- The ErrorBanner message + next step + 'Copy details' structure

### Open questions

- Request #1: should a per-model context replace the global 'Context size', or override it, with the global value as the default for models that have none?
- Request #1 'auto compresses': does the owner mean the existing automatic summarising of older messages (already on, barely visible) or automatically choosing a context size that fits memory when loading (suggestedCtx exists but is unused)? Should either be switchable?
- Request #2: which extra load settings should be exposed: device picker, GPU layers, thinking budget, prompt cache? Should advanced ones be hidden behind 'More options'?
- Request #3: which direction is meant? (a) The local model serves other assistant apps as their model, through an OpenAI-compatible local address. (b) The local model can call those apps as tools. (c) Something else. Should it be loopback only? Should requests from other apps go through this app's approvals and audit log?
- Request #3 wording versus the rule 'never put names or identifiers of AI models or assistants into code, comments, tests or docs': can the UI name the target apps, or must they be described generically ('other AI apps on this computer'), or supplied as data?
- Request #4: who writes 'what each model is good at', and where does it live? New fields in the signed catalog seem the only safe source. Is 'No description yet' acceptable for Hugging Face repos outside the catalog? Should the comparison include the user's own Tested settings and benchmark results?
- May existing labels pinned by e2e and unit tests ('Use', 'Local models', 'Tested settings', 'Check this model', the settings tab list, 'Ready on vulkan · Vulkan0 …') be renamed for plainer language, with the tests updated in the same change?
